# 通信业务结构体聚合 v1

一次命令的请求与回复由 `ProtocolExchange` 持有，分发和业务处理使用同一对象。
编码函数使用 `ProtocolResponse` 传递固定缓冲区和实际长度，移除零散的容量与长度参数。
`ProtocolMotor` 聚合操作与只读状态来源，APP 静态提供绑定。

维持两个通信实现文件。线路编号、字节布局、CRC、权限、业务结果、反馈顺序、
拥塞重试和 Loader 交接确认语义保持不变。结构体按字段编码，不直接映射线路内存。

修改前快照及构建保存在 `outputs/protocol-structs/baseline` 和 `before`。
验收执行黄金向量、实际接收入口链路测试、128,592组前后请求对照、完整 PR 检查，
并比较三个 APP 的 Keil 构建与资源。回退只恢复本次范围内的快照，保留其他工作。
本次仅离线验证。

## 结果

已完成。`ProtocolExchange` 持有消息和回复，各业务处理函数使用同一个对象。
六个编码函数使用 `ProtocolResponse`，编码成功时在对象内填写长度，反馈也使用同一载荷结构。
`ProtocolMotor.status` 与四个操作静态绑定，移除独立的 `Protocol_MotorStatusSource`。
原始字节只在编码和解码处处理，业务回调继续使用带单位的请求与结果值对象。

通信目录总行数1989 → 1918，减少71行，仍为两个实现文件和一个头文件。
128,592组请求前后轨迹完全一致，真实APP命令和状态回归的输出逐字节一致。
固定结构体替代短缓冲区接口，相应测试改为检查载荷长度、黄金字节和失败时保持输出。

最终完整PR通过，证据为 `outputs/runs/protocol-structs-verified-20261104/summary.json`。
124项单元测试、16项集成测试及全部原生回归通过，格式、静态检查、架构、接口、
工程布局和文档检查通过。迁移中的旧测试签名遗漏及格式问题已修复。

三套APP前后Keil构建均为0错误、0警告，资源按Code+RO+RW和RW+ZI统计。
