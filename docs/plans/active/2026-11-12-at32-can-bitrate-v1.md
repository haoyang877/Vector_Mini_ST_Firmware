# 五轴 AT32F456 通过 CAN 配置波特率 v1

本方案针对节点 3 至 7。起点为 the-system-refactor 的 ac153baa。五台台架已有的
500 kbit/s 仲裁、2 Mbit/s 数据及对应 TDC 配置来自该分支工作区，须作为缺省档纳入新包。
以下为设计和验收目标。

## 通信接口

复用现有参数服务，在目录登记单个设备参数 `0x71`，类型为 u32，读和停机写。
高 16 位存仲裁速率，低 16 位存数据速率，单位均为 kbit/s，小端编码。
仲裁允许 500、1000，数据允许 500、1000、2000、3000、4000、5000，两列独立选择。
整个 u32 校验通过才更新 RAM；沿用已有停机、实际关相、修订号、错误及重试语义。

以节点 3 从 500K/2M 改为 1M/3M 为例，主机在原速率上操作。

| 命令 | 请求 payload（十六进制，小端） | 预期结果 |
| --- | --- | --- |
| 120 读参数 | `71 00 00 00` | 读出待保存配置和当前 revision |
| 121 写参数 | `71 02 04 00 01 00 00 00 B8 0B E8 03` | 示例假定 revision=1，实际使用上一步返回值 |
| 122 保存 | 新 revision 的 4 字节小端值 | 接收 Flash 写入和回读结果 |
| 123 读已保存值 | `71 00 00 00` | 返回 `0x03E80BB8`，仍使用原速率 |

五台共线时按节点逐一完成上表，所有读回成功后统一重启五台，主机按新速率重开通道并核对 UID。
中途任何节点未保存成功时，仍能在原速率下重试或把已经保存的节点改回原配置。
该流程的生效点是重启。120 返回当前 RAM 参数，123 返回保存参数，均可能与正在工作的总线速率不同。

## 候选位时序

板上 CAN 时钟为 180 MHz，AT32 两段共用同一个预分频。下表采用厂商 SDK 的
`bts1_size + bts2_size` 计数；速率为时钟除以预分频与该和的乘积。
各段 SJW 取本段 SEG2。TDC 只在实际分频为 1 或 2 的列启用，偏移取数据 SEG1 + 1。
旧 500K/2M 档沿用原台架时序。

| 数据段 kbit/s | 实际分频 | 500K 仲裁 SEG1+SEG2 | 1M 仲裁 SEG1+SEG2 | 数据 SEG1+SEG2 | TDC 偏移 |

| 500 | 5 | 54+18 | 27+9 | 54+18 | 0 |
| 1000 | 5 | 54+18 | 27+9 | 27+9 | 0 |
| 2000 | 2 | 135+45 | 68+22 | 34+11 | 35 |

## CAN1 寄存器与启动顺序

五轴板的 CAN1 基址为 `0x40006400`。APP 和 Loader 都已调用厂商的
`can_bittime_set(CAN1, &timing)`（APP 的 `MCU_CAN` 即 CAN1）。将选定档位填入现有
`can_bittime_type`，由 SDK 完成下表的字段编码。传入 SDK 的段长和 SJW 使用实际 TQ 数。
[SDK 实现](../../../firmware/platform/sdk/at32f45x/drivers/src/at32f45x_can.c)、
[寄存器位域](../../../firmware/platform/sdk/at32f45x/drivers/inc/at32f45x_can.h)。

| 寄存器 | 地址 | 使用的字段及编码 |
| --- | --- | --- |
| `CTRLSTAT` | `0x40006428` | `RESET[7]` 控制配置窗口，1 为 CAN 本地复位，清零后参与通信。 |
| `ACTIME` | `0x40006404` | 仲裁段 `AC_SEG_1[8:0] = SEG1 − 2`、`AC_SEG_2[22:16] = SEG2 − 1`、`AC_SJW[30:24] = SJW − 1`（SDK 编码）。 |
| `FDTIME` | `0x40006408` | 数据段 `FD_SEG_1[7:0] = SEG1 − 2`、`FD_SEG_2[22:16] = SEG2 − 1`、`FD_SJW[30:24] = SJW − 1`。 |
| `LBTCFG` | `0x40006410` | 两段共用 `PRESC[4:0] = 实际分频 − 1`。数据段 `FD_SSPOFF[15:8]` 以 TQ 计，0 关闭 TDC。仅这两组位属于波特率配置。 |

以 1M/3M 为例，两个阶段共用实际 2 分频，仲裁段取 68+22 TQ，数据段取 23+7 TQ，
发送延时补偿偏移为 24 TQ。下表是按 SDK 编码所得的候选值，供 J-Link 以 32 位读取时对照。
`LBTCFG` 一列只列出掩码 `0x0000FF1F` 内的值，高位已有重仲裁和重发限制。

| 数据段 kbit/s | `ACTIME`，仲裁 500K | `ACTIME`，仲裁 1M | `FDTIME` | `LBTCFG & 0x0000FF1F` |
| ---: | --- | --- | --- | --- |
| 500 | `0x11110034` | `0x08080019` | `0x11110034` | `0x00000004` |
| 1000 | `0x11110034` | `0x08080019` | `0x08080019` | `0x00000004` |
| 2000 | `0x2C2C0085` | `0x15150042` | `0x0A0A0020` | `0x00002301` |
| 3000 | `0x2C2C0085` | `0x15150042` | `0x06060015` | `0x00001801` |
| 4000 | `0x5959010C` | `0x2C2C0085` | `0x0A0A0020` | `0x00002300` |
| 5000 | `0x5959010C` | `0x2C2C0085` | `0x08080019` | `0x00001C00` |

## 当前实现与验证

功能开发在独立工作树，APP v0.7.0、Loader v2.3.0 使用同一组档位。两端原生端口测试对 12 种组合逐一核对黄金寄存器、分频和两段速率。五轴 schema14 夹具通过保存、重载、CRC 损坏、旧槽与错误参数检查。主机工具验证了 120/121/122/123 的请求字节、状态拒绝和 Flash 回读不一致。
AT32F456 整机预构建通过，Loader 为 15160 B，APP 为 88312 B。合并 HEX 的有效扇区截至 0x08019FFF，参数从 0x0801C000 开始。台架先读到了 4 号电机的原始 500K/2M 实板时序，逐台烧录结果随本次构建另行记录在 outputs。

4 号已通过 J-Link 烧录、完整有效镜像回读、保护区逐字节比较和复位后 CAN 版本查询。旧输出轴扩展使整轴 `saved_revision` 为 0 时，123 仍能从有效基础记录读出 500K/2M。主机只读命令据 123 的结果显示 Flash 值。

4 号通过真实 CAN 在原 500K/2M 上把 0x71 的 RAM 值设为 1M/3M，修订号从 1 变为 2。120 读到新值，123 仍读到原值。随后用 121 恢复 RAM 为 500K/2M，并复核 RAM 与 Flash。该试验未保存或切换现场总线。

## 验收与回退

1. 对 12 组分别从 APP 和 Loader 的实参回算两段速率、采样点和 TDC，覆盖非法值、旧记录、CRC 损坏、停机门禁、版本冲突和保存后重启。核对协议黄金字节和现有标定回归。
2. 按 release 验证入口构建，生成可追溯的 AT32 Loader + LoaderApp 合并 HEX 和哈希清单；核对实际加载段及最后一个擦除扇区均在参数区起点 0x0801C000 之前。
3. 按台架既有 UID 对照节点 3 至 7。每台确认关相、备份完整 Flash 后按扇区烧录，读取并核对镜像、参数、身份和上半区。复位后在默认档查询五个 UID 和新参数。
4. 共线切档须协调五台和适配器。对实际测试的组合记录保存返回值、重启后速率和逐轴读回应答；保留最终 500K/2M。硬件覆盖与离线计算分别报告。必要时用对应 UID 的备份和上一个合并包恢复。
