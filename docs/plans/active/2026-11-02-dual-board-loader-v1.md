## 目标与边界

在重构分支复用现有 `loader/core`、`shared/image`、`shared/boot` 和公司升级协议，
新增 AT32 独立 Loader、配套 LoaderApp 及相应构建输入，使同一主机工具可显式选择两板升级。
完整链路为：APP 停机 → 56 交接回复真实发出 → 复位进 Loader → 50..55 下载、校验和激活
→ APP 一次试运行 → 57 健康确认。任何失败保持输出关闭，并允许重新完整下载。

本轮仅支持重构分支现有 CAN FD 1M/5M、单 APP 槽、CRC32 和现有 96B 镜像描述符。
不增加 UART、USB、A/B 回滚、Loader 自升级或签名；不重写电机控制核心。
G431的layout6、地址、参数ABI和线协议保持兼容。APP与Loader仍分别构建，
日常Keil APP入口统一采用配套LoaderApp布局；从0地址运行的独立APP不作为本方案的下载产物。

**通信协议冻结**：不新增/删除命令、GET_INFO 页、能力位或字段，不改变 CAN ID、波特率、
头部、长度、字节序、CRC、分片、结果码、会话语义或现有确认流程。保留 Type1 页0..2、
Type50..55、Type56 和 Type57。新增芯片目标的身份值通过现有字段表达，不改变字段格式。
main 的 1M/1M 标准帧协议 v2、0x66 及独立记录页不移植到重构分支。

## 评审结论与必须修正的问题

现有通用事务可以复用，但不能只新增目标 JSON 和一个 Flash 驱动。以下问题均纳入实施范围：

| 等级 | 发现 | 方案与验收 |
| --- | --- | --- |
| P0 | APP生成器只替换名为 `boot_hw_unavailable.c` 的条目，AT32工程实际编译 `boot.c` | 按目标声明的精确源路径替换，校验恰好一个BootHw实现 |
| P0 | `app.c`按板型直接选bringup头，配套AT32仍可能对外报告零身份 | 配套镜像使用生成的目标选择头，不把硬件分支扩散到业务代码 |
| P0 | 通用 APP scatter 只有普通 RO/RW/ZI，会丢失 AT32 的 `ER_FAST` | 增加有真实 AT32 调用方的链接布局选择，保留 56 KiB 快代码区和各段加载/执行语义 |
| P0 | `keil_loader_app.py` 只接受一个 APP Flash `PT_LOAD`，不能假定带 SRAM 执行段的 AXF 可原样通过 | 用真实 AT32 链接结果检查物理加载地址；需要时增加受控多段处理，保留原单段路径和拒绝边界 |
| P0 | SDK `SystemInit` 将 VTOR 写回 Flash 起点，重定位 APP 不能只依赖 Loader 先设 VTOR | 配套 APP 在开放中断前设置并复核自己的 VTOR；不修改厂商源码，普通 APP 仍从起点启动 |
| P0 | `App_Process` 的 `BspWatchdog_Feed` 与 `BootHw_Watchdog` 是两条喂狗路径 | LoaderApp 由统一健康/试运行期限判定授予喂狗；超时后所有路径停止喂狗。测试真实组合调用，不只测试单个 BootHw 函数 |
| P0 | 当前 Flash 参数端口使用 32 位写，镜像内核要求 8B 逻辑提交 | AT32 端口把一个 8B 单元映射为两次 32 位写，逐次检查错误、最终读回；任一步失败废弃本次会话，不原位补写 |
| P0 | 激活必须绑定那一帧的发送完成，不能用队列空或旧 TPIF 代替 | AT32 Loader 首版使用单个独占发送槽，保存完整 64 位票据；清除旧终态，确认成功/失败后只消费一次 |
| P0 | 原方案只要求构建合包，未覆盖main初装的备份、选择性写入及全片回读 | 本轮交付目标化初装工具，参数/身份和空洞不写，失败不发布成功或自动启动 |
| P0 | 重构分支GET_INFO仅有0..2页，没有main的完整16 KiB参数CRC字段 | 遵守协议不变要求，使用旁路SWD双次快照及离线CRC/SHA256；禁止增加CAN查询页 |
| P0 | Rust目标读取仍硬编码G431，独立Python/Rust升级路径可能分叉 | 两条路径显式选择同一目标契约，使用相同包/故障向量和验收定义，不新增第三套CAN升级实现 |
| P0 | 用户需要Keil直接下载APP且Loader/参数不变 | 独立LoaderApp工程只生成APP物理加载段，构建门禁拒绝保护区段，下载前后校验完整保护区 |
| P1 | 当前参数端口的轮询次数不能代表 Flash 墙钟超时 | Loader 使用独立自由运行计时源；停顿计入超时，Flash 忙故障不可无限喂狗；用 SRAM 临界实现或硬件看门狗保证终止 |
| P1 | 新板尚无生产身份页和正式目标编号 | 按下文登记身份页与目标编号；无有效生产记录时报告无效，不自动生成 SN 或改写参数 |

评审决定：采用“现有核心 + 新端口 + 配套 APP 定点修正”，不复制整套升级状态机，
不把 APP 整体 BSP 初始化带进 Loader。必要的 Flash/CAN 硬件代码可以在窄端口中复用实现思路，
不能因此启动 ADC、PWM、标定、参数写入或电机任务。

## 128 KiB预算与分区

两板统一预算：Loader16 KiB + APP96 KiB + 参数/身份16 KiB = 128 KiB。
代码、常量、向量、96B描述符、三个提交标记、SRAM热代码的Flash加载副本、RW初值及对齐填充
全部计入所属Flash分区；不能只相加Code统计，也不能把合包中的参数镜像另算一份。
正式工件必须证明每个加载段及整个分区预算满足约束，超限则构建失败，不能自动扩大分区。

G431沿用layout6：Loader `0x08000000..0x08003FFF`，APP `0x08004000..0x0801BFFF`，
参数/身份 `0x0801C000..0x0801FFFF`，总地址范围恰为128 KiB。

AT32目标名拟为 `yg_esc_v1_at32f456`。两板统一Flash布局如下：

| 区域 | 起址 | 结束地址（含） | 容量 | 权限 |
| --- | --- | --- | ---: | --- |
| Loader | `0x08000000` | `0x08003FFF` | 16 KiB | 普通升级/Keil APP直下只读；初装由SWD写入 |
| APP | `0x08004000` | `0x0801BFFF` | 96 KiB | Loader与Keil APP直下的唯一Flash写域 |
| 参数 | `0x0801C000` | `0x0801F7FF` | 14 KiB | 初次迁移后Loader/Keil APP直下只读 |
| 生产身份 | `0x0801F800` | `0x0801FFFF` | 2 KiB | 随完整16 KiB原样迁移；普通升级只读 |
| APP 快代码 | `0x20000000` | `0x2000DFFF` | 56 KiB | 保留当前 `ER_FAST` |
| 普通 RW/ZI/栈 | `0x2000E000` | `0x20016FDF` | 36 KiB − 32B | 保留现有执行分段，顶端扣除邮箱 |
| 交接邮箱 | `0x20016FE0` | `0x20016FFF` | 32B | NOINIT/不参与 scatter 清零 |

Loader 自身可以使用 `0x20000000..0x20016FDF`，与 APP 分时运行。
APP 描述符仍位于 APP 起址 + `0x200`；镜像长按 8B 对齐，三个标记偏移和 CRC 归一化规则不变。
16 KiB是每块板Loader的硬预算，不宣称已经测得体积；独立构建后记录实际Flash、静态RAM和栈余量。

AT32物理芯片仍是256 KiB，容量识别不得伪报128 KiB；运行布局的结束地址硬限制为0x08020000。
上半区不放代码、常量、参数或镜像副本，不通过外部填充或隐藏加载段绕开128 KiB预算。
旧参数源0x0803C000在首次迁移后可原样留存，仅作历史现场，运行代码不再读取，也不进入新布局工件。
原32 KiB Loader / 208 KiB APP方案撤销，不再扩大核心镜像容量或修改128 KiB限制。

RAM 只使用当前链接脚本已经使用的 92 KiB 地址范围；不把芯片的 96+12 KiB 标称容量直接拼成
连续 108 KiB。厂商[产品规格](https://www.arterychip.com/en/product/AT32F456.jsp)列出
CC 型号 256 KiB Flash、96+12 KiB SRAM 和 CAN FD；具体 RAM 映射、Flash 2 KiB 擦除几何、
32 位写入及 WDT 极限时间须在实施首步依据准确版本参考手册复核。
不启用额外 Boot memory，不改变选项字节或读写保护配置。

AT32旧尾页尚未分配生产身份，仍随完整16 KiB逐字节复制；无合法身份记录时报告无效，不生成SN。
不能把未知尾页清成FF，也不把原样迁移理解为已经取得有效生产身份。

## 目标与协议兼容

- 正式目标必须登记非零 `TARGET_MCU`、`TARGET_PRODUCT`、`TARGET_HARDWARE`、`TARGET_LAYOUT`
  及版本，不能使用 bringup 的零值，也不冒用 G431 芯片编号。
  MCU 编码规则、两板是否共享产品编号尚无仓库注册依据，列为 P0 的配置确认项。
  编号确认前可以完成端口与纯内存测试，不能发布或刷写用临时编号的固件。
- schema14、ABI `0x000E08F0`、2288B 参数记录以及节点解析沿用当前语义。
  参数空白/损坏时走现有救援节点规则，不凭默认值改变 Flash。
- AT32 首版沿用现有 v3 镜像/升级协议；物理写粒度转换不改变线格式。
  新布局使用独立登记值和黄金向量，G431/AT32 镜像必须互相拒绝。
- 若手册复核表明两个32位写不能满足现有标记的掉电判定，报告具体阻塞并停止对应适配；
  本任务不允许自行修改协议/镜像格式，也不能弱化半写校验。
- 保留主机默认 G431；新板必须显式 `--target yg_esc_v1_at32f456`。
  主机核对 UID、目标、布局、版本与 CRC 后才创建下载事务，升级后重新发现并确认同一设备。

## 完整参数保护与证据

保护域是新布局定义的完整16 KiB，包括14 KiB参数域、2 KiB身份页、记录外字节及历史残留，
不缩小到schema14的2288B，也不因空白、CRC坏或schema未知而清零、格式化或写默认值。
两板普通CAN升级及Keil APP直下均不得写Loader或这个16 KiB域；参数起址固定0x0801C000。
APP启动只读现有参数，禁止借升级自动迁移、保存、标定、设零或改变CAN ID。
参数不兼容时保留原始数据并报告不可用，不把“镜像可启动”当作“原参数已兼容”。

采用三层保证：

1. 固件与工件：Loader端口和镜像核心只接受APP槽写入；AXF/HEX检查所有物理加载段。
   测试向Loader和16 KiB保护域注入边界、溢出及坏包请求，要求零写入。
2. 主机只读旁路：明确选择同一UID的SWD探针，升级前后各读两次完整保护域，先核对同次两份一致，
   再比较前后逐字节、CRC32与SHA256；同时核对CAN UID与SWD UID。
   CAN升级还比较整个Loader分区；不能只比较实际Loader BIN的已用前缀。
3. 初装/验收：保留完整物理Flash两次一致的备份和结束回读，除本次允许的APP/Loader安装区域外，
   所有字节须与起点一致。首次AT32迁移另允许写新参数区，但须与旧址16 KiB完全一致；
   普通APP更新唯一允许变化的区域是APP。

不通过CAN新增参数CRC、Flash读取或快照命令。现有Type1页0..2只用来核对既有身份、
版本、布局和镜像信息；旧在线参数读写/保存的UNSUPPORTED行为保持不变。
SWD读取集中安排在CAN事务前后，不插入分片或块重试窗口，不通过暂停/复位CPU取得“成功”快照。
探针被Keil占用时先释放该连接再执行旁路核对，不自动换探针或争抢同一调试端口。

纯CAN工具仍可完成现有v3升级及健康确认，其结果写 `upgrade_success`；
未做SWD比较时，独立的 `protected_regions_verified` 必须为false/NOT_RUN。
只有保护区验证也完成才能把带保护验收的整次作业标为PASS，不能把两个结论合并或隐去未测项。
这些字段只用于主机证据，不是新增线协议字段。

schema10仅保留为main历史快照查看格式；当前双板按schema14解码保存值，分别显示节点、
电机模型、编码器标定/线性化表、零位及保存标志。未知格式只保留原始文件。
保存标志不等于标定有效，节点名称不等于生产SN。迁移与生产身份写入不是普通升级的副作用。
G431本轮按重构分支既有schema14/layout6验收；如果现场仍是main的schema10，
不能一边保持参数字节不变一边宣称新APP已能使用旧标定。此时先备份并报告格式不兼容，
不自动运行历史schema转换工具。本次已确认的迁移仅指AT32现有schema14的物理地址迁移。

### AT32首次迁移事务

仅供旧布局首次转为128 KiB布局，操作入口与普通APP下载分离，执行时须有该板的明确台架上下文。
旧参数与新参数均为schema14，本次只变地址，不经过schema转换器、不重建默认值。

1. 绑定实际AT32 UID，完整读取256 KiB物理Flash两次并验证一致；另保存原16 KiB参数区双份，
   记录来源地址、长度、CRC32和SHA256。按明确旧布局与schema14校验记录，不能靠猜测识别。
   空白/损坏/未知格式只允许备份，不自动修复或宣称参数可用。
2. 生成仅属于该UID的迁移计划，引用备份哈希；通用分发包不包含该板个体参数。
   检查目标0x0801C000可能属于旧APP代码，进入受控初装后不能继续运行旧APP。
3. 保持关相并控制复位/暂停，将完整原16 KiB写到新地址，读回两次均须与源逐字节一致；
   原地址不擦写。随后安装配套Loader和未激活APP，结束前按整片预期再次核对迁移结果。
4. 仅在新参数、Loader和APP全部验证后提交激活、复位并运行新APP；新APP及普通独立构建的
   参数地址来源同步到新目标，禁止继续从旧址读参数而造成“复制成功但没有使用”。
5. 迁移失败不自动复位运行。恢复旧布局必须使用本板已核验的完整备份，通过独立恢复步骤执行；
   只恢复APP而混用新旧参数地址不算有效回退。

后续Keil下载只使用APP工程。迁移工具默认拒绝已是新布局的重复迁移，不将旧地址残留当成最新参数。

## Keil直接下载APP

正式支持两板各自的LoaderApp工程。用户在Keil直接Build/Rebuild、Download，
不要求每次重刷Loader，也不通过合并HEX替代APP调试下载。

- 由同一目标清单生成scatter、IROM/OCR内存项、APP入口、邮箱和后处理。
  APP物理Flash加载范围固定为 `0x08004000..0x0801BFFF`；两板均只有96 KiB。
- 后处理校验全部加载段、描述符、CRC、实际版本、RAM执行代码的Flash副本及8B对齐，
  调试AXF的三个启动标记在APP槽内预置有效。派生HEX/BIN来自该AXF，失败使本轮下载工件失效。
  不能只修改BIN而让Keil继续下载旧AXF；G431结果需保持现有单段后处理一致。
- 生成的APP工程下载配置采用按扇区擦除与编程校验。下载不包含Loader、参数、身份或未分配空洞；
  不执行整片擦除，不下载FULL/combined HEX，不在APP后处理调用初装烧录命令。
- 启动通过复位从既有Loader进入APP，不以强设PC/MSP/VTOR跳过校验。
  从0地址运行的bringup/独立APP不进入日常下载工作区；日常入口明确选择配套LoaderApp。
- 下载前保存同一UID的Loader整分区和16 KiB保护区；下载结束释放Keil探针后双次读回并逐字节比较。
  可复用main布局检查与Loader回读的思路，但删除旧脚本的历史BIN自动回退和固定G431地址。
  不承诺Keil能强制拦截操作者手动全片擦除；验收针对随包提供的正确APP工程及下载配置。
- 两板各验证“首次下载→修改APP→再次Download→断电启动”，检查APP确实更新，
  Loader及整个16 KiB参数/身份域保持原字节，验证AT32热代码和邮箱不被下载算法工作RAM破坏。

Keil调试镜像预置确认与现有G431行为一致；它不替代CAN升级的一次试运行与Type57健康确认。
两条路径用不同产物标识，禁止把调试AXF当作未确认CAN包或把CAN包直接当Keil AXF下载。

## 初装与维护工具

双板初装复用main的流程保证，具体地址、芯片校验、关相读回和下载算法由所选目标提供。
不是把main的48B记录页搬到v3中，普通APP更新更不会再次走初装。

1. 离线核对目标、组件版本、分区预算、全部哈希、向量和描述符；未知/混配包在连接设备前拒绝。
2. 显式选择探针及UID，核对实际芯片容量、功率关闭和设备独占；保存两次一致的全Flash备份。
   既有WDT在调试暂停/下载期间的处理须按两板分别验证，不假定halt会停止计时，不改选项字节绕过问题。
3. 受控暂停后按APP槽擦除并保持未激活，写入匹配Loader与未激活APP；
   每组件读回核对，整片只允许本次声明区域变化，参数/身份/空洞保持原字节。
4. 全部核对通过后最后写入现有v3激活标记；试运行/确认标记保持擦除态。
   再次核对全片，按显式启动选项复位并走既有Type57确认，不提前把试运行标为健康。
5. 失败保留现场、备份、错误和原始请求；不自动重擦、复位或恢复运动。
   初装中断可能需要SWD恢复，不能套用CAN单槽下载的可驻留保证。

现有debug FULL HEX（三个标记已确认）继续服务明确的调试部署；新增初装用途工件清晰区分，
仍使用原v3描述符，不改变任何线字段。初装工具控制“组件验证后最后提交”的顺序，
不能以普通HEX批量写入顺序替代事务保证。

维护能力在现有Rust界面与共享工具中承接：初装、CAN升级、版本/状态、保存参数/标定查看。
不复制Tk工程，不新增运动、参数写入或标定命令；GUI不能只显示控件却把后台尚未实现算作交付。
目标、UID、文件或探针变更使之前的绑定失效；任务互斥、失败后重新绑定、输出目录不能覆盖。
复用已有发布依赖和DLL打包能力，记录工具及依赖哈希；驱动加载成功不算硬件升级验收。
日志保留每次请求/重试、分阶段耗时、前后保护区哈希、源/目标/工件、失败原因及最终CPU状态。

| 初装与调试区别 | Keil调试预确认镜像沿用；初装按未激活写入后最后提交，不冒充已完成CAN健康验收 |
| 证据可信度 | main历史100轮只作为参考，双板新包分别验收；原42项/quick是旧方案基线，不冒充新实现通过 |
