# APP Flash 超限原因复核（2026-09-28）

本次针对“为什么超出这么大”复核分区、实际调用链和编译选项，基于提交
`e34deec617b503f33d64ed23220665209618e21d`。正式固件源码、工程选项和布局未修改；
所有对照在 `outputs/capacity-fit/causal-audit/` 的隔离副本中进行，无硬件操作。
这是容量分析，不是发布验收。

## 1. 40288 B 缺口是怎样形成的

目标 `STM32G431CBUx` 的 Flash 为 128 KiB，唯一布局输入为
`shared/targets/vector_mini_st_g431.json`。

| 区域 | 大小 |
| --- | ---: |
| Loader | 28 KiB |
| 启动记录 | 4 KiB |
| 镜像记录 | 2 KiB |
| APP | 78 KiB |
| 参数区 | 16 KiB |
| 合计 | 128 KiB |

普通 APP 原有 112 KiB 可用空间，当前实际占 111680 B，即 109.0625 KiB，
只余 3008 B。Loader 配套 APP 的 ROM 为 120120 B；向量表到固定描述符之间
还需 40 B 间隙，实际加载跨度为 120160 B，即 117.34375 KiB。

因此缺口可以精确分解为：

```text
普通 APP 到新布局减少的预算             34816 B（34 KiB）
Loader 配套 APP 增加的代码、数据及间隙    +8480 B
普通 APP 原有余量                       -3008 B
----------------------------------------------------
超过新 APP 区域                         40288 B（39.34375 KiB）
```

主要矛盾是接近 112 KiB 的 APP 被分配到 78 KiB 区域，启动集成又增加了约
8.28 KiB。不能说 Loader 给 APP 增加了 40 KiB，也不能把全部缺口归因于目录重构。
此前容量预算与最终链接产物没有闭环；布局落地不代表容量适配已完成。

本次未用同一工具链重建重构前提交，因此不声称证明了“重构新增多少字节”。
旧协议文档中约 88 KiB 的历史描述不能继续作为当前分区依据。

## 2. APP 的大头确实是保留代码

以下按当前 map 中对象的 Code + RO 聚合；不重复累加 inc. data，也不把 RAM
中的 ZI、调试符号或 AXF 文件大小计入 Flash。

| 类别 | Code + RO |
| --- | ---: |
| 电机算法、位置控制、轨迹和标定 | 38742 B |
| 平台、HAL、初始化及硬件端口 | 27494 B |
| 应用状态、调度和维护适配 | 18300 B |
| 通信 | 10427 B |
| 参数等服务 | 7410 B |
| 共享协议、镜像和记录契约 | 6448 B |
| 通用数学和内存工具 | 5034 B |
| RTT | 520 B |

此外有 5554 B C/数学运行库，以及 191 B 链接填充与压缩初始化数据，ROM 合计 120120 B。
例如正弦表为 4096 B，HAL 对象合计 18496 B；后者含当前实际初始化与中断路径，
不能全部当成冗余删除。维护内存池主要占 RAM，缩池不是解决 Flash 超限的方法。

## 3. 已实测的冗余：无新入口的旧模式仍被链接

`FocRunState_RequestEnable()` 和 `validate_control()` 仅接收电流、速度、位置、
Vq 四种控制模式。维护入口的映射以及 worker 的内部模式转换，也不进入旧的
`Position_Impedance_Mode`、`Sensorless_Speed_Mode`、`Voltage_OpenLoop`。

然而 `FocMode_Dispatch()` 仍包含三个 case，链接器因此保留它们引用的代码。
具体调用链包括：

```text
FocMode_Dispatch
  -> Task_Position_Impedance_Mode
     -> PositionImpedance_Update / 摩擦处理
        -> TRAJ_plan / TRAJ_eval
```

仅从实验源文件副本删去这三个调度 case，其他代码、配置、算法和工程输入保持，
重新编译后 ROM 从 120120 B 降为 113688 B，实际减少 **6432 B**。
其中阻抗对象从 4790 B 降至 12 B（其他路径仍调用 Reset），旧梯形轨迹对象
748 B 全部移除；其余收益来自对应包装函数、FOC 电压路径和辅助函数。

这修正了此前“存在调用就视为当前有效功能”的粗略判断：旧 switch 的引用
不等于存在受支持的产品入口。正式删除仍需清理枚举、状态投影、配置与文档，
并用当前模式回归确认边界，不应把实验副本直接当作完成的变更。

无感运行对象仍有 3072 B 留下，因为当前编码器观测器标定实际依赖它；不能
因删除旧无感速度入口就把整个观测器/无感模块删除。

## 4. 已实测的配置问题：状态机使用时间优化

`foc_run_state.c` 实际编译命令是 `-O3 -Otime`，不能只看全局空间优化选项。
其 Code + RO 为 9332 B。用同一工具链、同一源码，单独重编该对象后重新链接：

| 隔离实验 | APP ROM | 加载跨度 | 相对当前减少 |
| --- | ---: | ---: | ---: |
| 当前配置，隔离副本复现 | 120120 B | 120160 B | 0 B |
| 仅移除三个旧调度入口 | 113688 B | 113728 B | 6432 B |
| 仅状态机 O3 + Ospace | 119032 B | 119072 B | 1088 B |
| 仅状态机 O1 + Ospace | 119512 B | 119552 B | 608 B |
| 旧入口移除 + 状态机 O3/Ospace | 112608 B | 112648 B | 7512 B |

组合实验仍超出 78 KiB 区域 **32776 B**。组合收益与单项和相差 8 B，来自
链接布局/对齐，不能把独立实验数字直接累加。降低优化等级也不保证体积更小。
此处只证明尺寸变化，没有证明状态机、快速环或中断执行时间满足要求。

加载跨度读取 map 的 `LR_APP COMPRESSED[...]`；未压缩的 Load Region Size
还含压缩前 RW 初始化长度，不能代替实际镜像尺寸。

## 5. Loader 集成增量和后续优先级

APP 的启动集成确实引入镜像身份检查、SHA256、记录读写、试启动确认、停机交接
和状态守卫。当前 map 中 image_transfer 为 1884 B、nv_record 为 1516 B、
SHA256 为 1110 B、启动硬件端口为 1426 B、交接服务为 962 B。
完整下载、分块写入等未用函数已经被链接器移除；并非整个独立 Loader 被重复链接。
这些模块还包含必要的安全契约，进一步瘦身需逐个核对责任边界。

独立 Loader 实测占 20036 B，但预留 28672 B。即使按 2 KiB 页取整至理论
最小 20 KiB，也只能回收 8 KiB，且仅余 444 B，不适合作为有增长余量的最终预算。
镜像记录、启动记录和参数区均有持久化用途，不能只为通过链接而随意挪走。

建议执行顺序：先清除已证实无入口的旧功能闭包；再逐模块测空间优化、表压缩和
重复适配；同步压缩 Loader 及 APP 启动集成的实际实现，最后依据实测重定分区。
电流/速度/位置控制、有效标定、STOP/FAULT 和完整性检查不作为静默裁剪对象。
不能承诺只删历史兼容分支就填平 39.34 KiB，是否需要进一步产品功能取舍，要用
剩余模块的测量结果判断。
