# 开发流程

`develop` 是默认分支，承接日常开发和集成。`main` 承接正式发布和在役版本维护。
APP、Loader、上位机和 STM32G4 / AT32F456 板型共用开发线，按实际组件和板型验证及交付。

## 分支与合并

| 分支 | 起点与合并目标 | 用途 |
| --- | --- | --- |
| `feature/*`、`fix/*`、`codex/*` | 从最新 `develop` 创建，提 PR 合回 `develop` | 每个分支只处理一项需求或修复。普通任务用 squash merge。 |
| `release/*` | 冻结发布候选时，从已集成的 `develop` 创建，验收后提 PR 合入 `main` | 收敛发布阻塞问题。发布用 merge commit。 |
| `hotfix/*` | 从实际交付版本的标签创建，提 PR 到对应的发布或维护分支 | 修复在役版本，同一任务将修复通过 PR 回流到 `develop` 并关联原 PR。 |
| `maintenance/*` | 从实际交付版本的标签创建 | 只在旧版本需要继续交付补丁时建立。 |

`develop` 和 `main` 通过 PR 合并，关闭强推和删除权限。合并前解决评审讨论。
`main` 还要求一位有仓库写权限的评审人批准。
短分支合入并确认关联工作树的未提交修改和本地产物已妥善保存后，可以清理。

## 日常开发

1. 从所属[设计与协议](../README.md)定位需求及验收。写清改动范围、影响的组件和板型、兼容要求及验证方式。
2. 从最新 `develop` 开短分支，保留其他任务的本地改动。实现时同步更新调用方、工程输入和相关文档。
3. 按[项目工具](project_harness.md#验证级别)选择验证级别。PR 写明改动动机、受影响的目标、验证证据和未测项。
   涉及协议、参数 ABI 或升级行为时，同步版本、兼容说明、黄金向量及对应测试。
4. 检查 PR 差异范围，核对最新提交的验证结果并处理评审意见。台架验证按明确设备和场景执行。

## 发布与回流

在发布候选上明确组件、板型、配套版本及 `target_profile`。按[固件发布规范](firmware_release_standard.md)
核对布局、协议和参数兼容性，以及适用的启动、通信、升级和台架验收。

合入 `main` 后，以最终提交的 `summary.json`、发布清单和产物 SHA-256 核对实际交付内容，再打版本标签。
候选验收镜像与最终交付镜像的哈希不一致时，按最终镜像补做受影响的验收。正式发布的修复与历史通过 PR 回流到 `develop`。
