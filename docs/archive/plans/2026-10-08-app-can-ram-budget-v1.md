# APP CAN FD 静态 RAM 缩减计划 v1

日期：2026-10-08。范围仅为 APP 的 CAN FD 组合层；Loader 的升级接收缓冲和公共协议
端点上限保持独立。

## 目标与依据

优化前 APP 为发送端预留 40 帧，以覆盖通用端点最大 1767 B 消息的 39 个分片；
实际 APP 主动反馈及自动业务回复均为单帧。控制命令历史原预留 256 条，但当前
代码只要求近期重发可重放原结果；已被覆盖的旧序号仍由递增水位拒绝，不再执行。
RX 的 8 帧占 608 B，负责吸收中断到主循环之间的突发输入，暂不缩减。

## 变更与不变项

- APP TX 从 40 帧改为 8 帧。控制请求处理前继续预留回复与反馈两个位置；
  发送受阻时保留 RX 请求并施加背压。
- 控制历史从 256 条改为 32 条。窗口内相同序号和 payload 重发原结果；
  窗口外的旧序号返回旧序号错误，不重新提交电机目标。
- APP RX 维持 8 帧；通用端点的长消息能力和 APP 的 1767 B 接收重组区维持不变。
- 线上帧布局、结果码、电机状态机、Loader 升级协议、Flash 布局及安全停机
  行为不变。APP 不再保证能一次排入 39 片长发送消息；当前没有此类真实发送入口。

## 兼容边界与验收

主机若跨过超过 32 个更新的控制序号才重发旧请求，可能收到旧序号错误，
而非原结果。此时主机应读取状态确认，不能把旧控制命令改用新序号盲目重发。
实时控制的长期重试规则仍需单独冻结；32 条历史不能代替 1 s 的事务结果保存。

验收包括：TX 堵塞时不重复执行、恢复后回复保持顺序；窗口内重发保持幂等，
窗口外重发明确拒绝；PR 验证通过，release 构建后的 MAP 显示 RAM 下降。
回滚是恢复原两个容量，重新运行相同验证；不涉及持久数据迁移。

## 离线结果

正常 APP 构建成功，0 错误、0 警告。其 MAP 静态 RAM 为 26904 B；此前同目标
31576 B，下降 4672 B。其中 TX 缩减 2432 B，历史缩减 2240 B；该对象的 BSS
由 8536 B 降至 3864 B。每个物理帧结构在 ARM 目标上占 76 B，含元数据和对齐。
这是 2026-10-08 的缩减对比；当时正式 release 验证因工作树存在其他未提交改动
而拒绝冻结证据，配套 LoaderApp 当时也尚未链接成功。

2026-10-09 在干净的 `codex/system-refactor@8c422ef` 上重新构建：普通 APP 静态
RAM 为 18336 B，配套 LoaderApp 为 18392 B；后者相对 32736 B 可用 RAM 仍余
14344 B。配套镜像离线打包和检查通过，硬件升级测试尚未执行。这次总量下降还包含
后续电机核心精简，不能全部归因于本计划的 4672 B CAN 缓冲缩减。

当前不继续缩小 RX 8 帧或 1767 B 重组区：RX 承接中断突发，重组区保持通用端点
已声明的长消息上限；进一步缩减需要实际流量/丢帧证据和协议兼容性评估。
