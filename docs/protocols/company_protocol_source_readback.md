## 2. 设计目标原文摘录

> 一套应用层协议：所有应用数据（USB、CAN、内部 IPC）跑同一种帧格式，协议不感知物理链路。

> 传输分层：协议只定义消息（类型 + 字段 + 序列化），USB/CAN 只是载体——同一消息在 USB 上多帧打包，在 CAN 上单帧承载，超限分片。

> 无翻译层：协议统一后，RV1126B 收到 USB 消息原样转发到 CAN（反之亦然），不存在 Bridge 字段级映射。

> 控制帧确定性：实时控制类消息强制单帧、禁止分片，保证 CAN 仲裁下确定性时延。

> 零解析开销：固定字段布局，MCU 侧 memcpy 直接解包，不引入序列化库。

> 校验分层：USB/CAN 硬件 CRC 兜底物理包传输；应用层帧尾 CRC16 兜底串口等无硬件校验链路，双保险

## 3. 原文帧格式与字段

```text
协议帧 = [ 16B 统一帧头 | payload | 2B CRC16 ]
        └── 所有链路同一种帧，不区分 USB / CAN / SHM
```

| 偏移 | 字段 | 大小 | 原文字段内容 |
| ---: | --- | --- | --- |
| 0 | magic | 2B | 0xA55A，帧同步 |
| 2 | version | 1B | 协议版本 = 0x01 |
| 3 | flags | 1B | 分片、请求 ACK、req/ack、上报请求、重传与预留位，见下文 |
| 4 | src_id | 1B | 源节点 |
| 5 | dst_id | 1B | 目的节点，0xFF 广播 |
| 6 | type | 2B | 消息类型；ACK 时复用请求 type |
| 8 | seq_id | 2B | 帧序号，单调递增，重传序号不变；ACK 时复用请求 seq_id |
| 10 | len | 4B | payload 长度 |
| 14 | 预留位 | 1B | 预留1B |
| 15 | 帧头 CRC8 | 1B | poly=0x9B，init=0x00，xorout=0x00，refin/refout=false；原文称覆盖帧头、每片独立 |
| 16 | payload | 可变 | 消息体；CAN FD 单帧上限 46B |
| n | 帧尾 CRC16 | 2B | poly=0xBAAD，init=0xFFFF，xorout=0x0000，refin/refout=false；覆盖帧头+payload，每片独立 |

原文第 9 节明确采用“小端字节序（与现有平台一致）”。整帧长度为 `16 + len + 2`，len 不含帧尾 CRC。原文 payload 说明行另出现“CRC-16/CCITT”，与末行自定义参数的称呼需核对。

第 3.1 节 flags 描述：

1. flags[7:6] 分片标记，flags[5] ACK 标识位，其余保留。
2. [5] 是否需要 ACK（置 1 时，接收方处理完回一帧 ACK，用于日志、OTA 这类需要确认的场景）。
3. [4] req 还是 ack（0 为 req，1 为 ack）。
4. [3] 是否为上报请求（1 为上报请求）。
5. [2] 是否为重传（1 为重传）。
6. [1:0] 扩展预留（优先级、压缩、加密等）。

第 3.3 节另规定：flags[7:6] 为 `00 单帧 / 01 首片 / 10 中片 / 11 尾片`，flags[5] 为“1 = 请求确认或本帧为 ACK”。这里与 3.1 中“其余保留”、bit4 的区分方式需要统一。

第 3.3 节其他内容核对：

- len 4B 用于支持 2MiB 图片等大消息。
- 时间戳不占帧头，按需放 payload 尾部；Log、跨节点事件等需要，控制/心跳/状态类不带。
- seq_id 2B：分片消息内作为片序，首片为 0；重传引用缺失片，不另设 frag_index。
- 单帧或分片时 len 都是当前帧 payload 长度，尾片标志决定重组结束。
- 原文称“len 4B 位于 4 字节偏移处，嵌入式解包无坑”；字段表实际偏移为 10，需要修订说明或布局。

## 6. 原文分片与重组

- 重组键为 `(src_id, type)`；seq_id 提供片序，flags[7:6] 提供首/中/尾。
- 首片创建缓冲，按 seq_id 顺序拼接，尾片完成重组。
- 重组超时：实时控制类 50ms、状态/心跳类 200ms、日志/小分片类 500ms；OTA/大块数据类按块大小、链路速率和负载动态配置。
- MotorCmd/EStop 等实时控制消息禁止分片，payload 超过 46B 直接报错。
- 分片面向 OTA 块、日志等中等消息；2MiB 图片走 USB 单帧。
- 原文认为 CAN 硬件自动重传与停等 ARQ 保持顺序；流水线窗口 ARQ 或多路径场景需要按 seq_id 重排。
- 原文第 6 节写“一条协议消息 = 一个 URB”，并讨论 512 整数倍的 ZLP；第 8.1 节则允许一次 bulk 打包多帧并提及 SS 1024B maxPacketSize，两处需要按实际 USB profile 明确。
- ACK：请求方置 flags[5]=1；接收方回同 type、同 seq_id 并置 flags[5]=1；与 flags[4] 的配合需定版。
- 超时丢弃未完成消息，CRC 错误丢帧，重组失败记录 seq_id 不连续、flags 标记错误等原因。

## 7. 原文校验设计

- 物理层：USB 硬件 CRC16＋重传，CAN FD 硬件 CRC17/21。
- 帧同步：magic 不符拒帧并重新同步。
- 残缺帧：检查 `16 + len + 2` 长度自洽。
- 丢帧：seq_id 跳号用于丢帧质量监控。
- 原文认为逐片校验与确定性重组足够，因此“不需重组 CRC32”；这是原文观点，不应据此取消升级镜像的整包摘要/签名校验。
- 帧头 CRC8 参数为 0x9B/0x00/0x00；帧尾 CRC16 参数为 0xBAAD/0xFFFF/0x0000；均非反射。

## 8. 原文传输适配层

| 承载 | 已读规定 |
| --- | --- |
| USB Bulk | 连续帧流，magic 同步；一次传输可打包多帧；复用 usb_bulk 的 ZLP/ENOMEM 背压/SS 1024B maxPacketSize；2MiB 图片单帧 |
| CAN FD | 64B = 16B 头 + 46B payload + 2B CRC；控制消息 CAN ID 优先，状态其次；仲裁 500k，数据 2～5M |
| 经典 CAN | 主要讨论供应商 BMS 8B 协议，由 RV1126B 转成 BmsState；不是已定义的通用升级承载 |
| 内部 IPC | 同一帧格式内存拷贝；媒体走 SHM 零拷贝环形缓冲，meta 走协议帧 |

原文还有“64B 帧总线时间约 0.36ms，1kHz 双向负载 <30%”以及“心跳 1Hz，连续 3 次丢失 → 急停”。前者数量关系需重新预算：若每方向每周期各一帧，按其 0.36ms 估算已是约 72%，并非 <30%；后者需区分设备在线心跳与运动控制目标超时。

RS485 和以太网没有在这份主文档中形成完整适配规范，需作为后续扩展明确。

## 9. 原文序列化与评审状态

- 每类消息一个 C 结构体，syscomm_msg.h；payload 为结构体原始内存。
- 小端字节序，字段按 4B 对齐编排。
- MCU 使用 memcpy，不引入 protobuf/nanopb/DDS IDL。
- 第 10 节没有展开具体消息结构。
- 第 11 节列出嵌入式、算法、安卓、后端；算法栏标记“通过”，其备注询问 1126B 内部基于 ROS2 裁剪的 topic 通信是否需改底层及改动时机；其他结论栏未见填写。不能称整份协议已全部评审通过。

## 10. 后续设计必须遵循的结论（建议，不是原文）

1. 电机与升级均复用公司 16B 帧头、type、src/dst、seq/ACK 和 CRC 体系；不另外创造一套互不兼容的外层升级 PDU。
2. 升级会话、镜像身份、offset、块长度、业务结果和恢复检查点放在升级消息 payload；与具体通信接口解耦。
3. 复用或补全公司分片适配规则；Flash 写入成功确认与链路/分片接收确认分开定义。
4. 升级块大小通过能力协商确定，不固定为 40B 或 46B；实时控制仍执行原文的单帧限制。
5. 新增 RS485/TCP/UDP/经典 CAN 升级适配；不假设原文已有这些完整规范。
6. 先解决 ACK 位语义、CRC8 覆盖范围（是否排除自身）、CRC16 命名、len 偏移、分片重组键/并发和 USB 边界的歧义，再形成测试向量与正式扩展。
7. 当前项目旧 CAN float 协议是大端，而公司协议小端，必须由明确版本/协议入口分流，不得在原命令号下静默切换字节序。
