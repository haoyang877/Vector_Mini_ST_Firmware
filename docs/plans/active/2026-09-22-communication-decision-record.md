## CAN FD 位时序

当前 STM32G431CBU6 的 FDCAN 内核时钟为 170 MHz。采用 1 个同步时间量子、12 个
TimeSeg1、4 个 TimeSeg2：

```text
总时间量子 = 1 + 12 + 4 = 17
仲裁段 = 170 MHz / (10 × 17) = 1 Mbit/s
数据段   = 170 MHz / ( 2 × 17) = 5 Mbit/s
采样点   = (1 + 12) / 17 = 76.47%
```

`.ioc` 和 FDCAN 初始化覆盖已按该配置更新。公司原文阅读记录中出现过 500 kbit/s
仲裁段；本项目现在采用 1/5 Mbit/s，属于已确认的产品部署配置，发布前仍要用实际收发器、
线束和总线分析仪验证误码和采样点裕量。

## 当前不能从公司原文直接推导的内容

飞书关联消息表中电机 100～199 段仍为空白，升级命令也没有完成登记。因此，以下内容只能先
作为项目候选，不能写成公司已批准的命令号：

- 电机控制、状态反馈、参数、标定和升级的具体 `type` 值；
- flags bit5/bit4 的最终 ACK 语义；
- 公司正式的 CAN ID priority/PF 映射表；
- 反馈帧是否由每轴独立周期发送，还是允许主站配置发布集合；
- 升级镜像格式、Loader 地址边界、镜像最大长度和签名策略。

1 kHz 设计建议采用“一条多轴控制组帧 + 每轴一条反馈帧”：组帧内携带至少 5 个轴的目标和同一
`cycle_seq`，反馈帧按轴返回状态和该周期序号。若给每一条 1 kHz 控制帧再单独发送 ACK，控制和
反馈流量会成倍增加，必须用实测总线利用率证明可行；因此建议实时控制用反馈回显 sequence/result
作为周期性确认，显式 ACK 只保留给需要可靠事务的管理类请求。

在登记完成前，代码可以继续使用显式的项目候选常量和黄金向量，但必须标注
`PROJECT_CANDIDATE`，禁止把候选 type 发布为公司正式兼容承诺。

## 还需要冻结的 8 项输入

1. **板卡 3/4 的角色**：Node 0x03 是否固定为左电机、0x04 是否固定为右电机；0x05～0x07 是否分别固定为 ROW、PITCH、YAW。
2. **10 ms 的含义**：是实时周期的最大允许抖动，还是允许数据缺失/超时的容忍窗口。1 kHz 周期是 1 ms，建议把 10 ms 定义为故障容忍窗口，并另外给出调度抖动指标。
3. **实时控制丢帧策略**：暂不启用通用看门狗时，连续丢失控制帧如何处理。建议保留“目标保持到一个明确的短期限，过期进入安全停止”的设备级策略，不能使用 1 s 事务超时直接代替它。
4. **命令登记**：公司是否批准项目在 100～199 段登记电机命令，并确认具体编号。
5. **参数保存边界**：哪些参数允许运行中写入，哪些只能停机写入；SAVE 是否立即擦写 Flash，还是只提交到参数服务队列。
6. **升级 Loader 契约**：Loader API、镜像格式、最大镜像、分块大小、hash/签名算法和 App/Loader 地址布局。
7. **实时控制应答**：确认采用“反馈回显 `cycle_seq`/执行结果”作为 1 kHz 控制的回复，还是要求每帧显式 ACK；推荐前者。
8. **总线容量策略**：确认首版是单路 CAN FD，还是允许双路分担 5 轴；若单路实测余量不足，确认是否由能力协商把控制/反馈降到 500 Hz。当前保守模型下，单路 1 Mbit/s / 5 Mbit/s 的“一条组控制帧 + 五条 32 B 反馈帧”约占 84.3% 周期带宽，不能直接承诺硬实时。
