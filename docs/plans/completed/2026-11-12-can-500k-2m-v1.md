# CAN FD 500K/2M配置

基线：the-system-refactor，ed66253f及现有未提交1M修复。保留用户修改与所有台架数据。
目标：双板APP、Loader和主机默认值统一为仲裁500kbit/s、数据2Mbit/s。
版本仍为APP0.6.2、Loader2.2.0；保留参数ABI、Flash分区、FD+BRS及全部线协议。

STM32G431 170MHz：仲裁20分频、数据5分频，均使用1+12+4个TQ。
仅修改现有USER CODE覆盖和CubeMX输入；首次生成配置的旧初值在启动CAN前被覆盖。
AT32F456 180MHz：共享2分频，仲裁135+45个TQ，数据34+11个TQ。
TDC偏移35TQ，实际分频2符合手册约束，避免重现历史分频5开启TDC的错误。

验收：真实双板初始化及Loader位时序测试、主机默认值测试、release检查、六目标构建。
用户追加授权：离线验证后，对既有5台AT32逐台烧录合并包并验证新速率通信。
逐台绑定既有UID，完整双次备份、镜像回读、保护区逐字节比较；复位后31次只读查询并确认参数不变。
保留板上各自的参数和身份，不发送运动指令；用户配合逐台换接J-Link及CAN。
证据归outputs/can-500k-2m；回退从该目录baseline-files.zip恢复本次修改前内容，
文档对照本计划与当前差异恢复，不覆盖用户无关修改。

用户确认五台共用CAN总线并通电。节点5单台先改速率时出现固定帧异常，不能据此判定单台固件。
先完成五台烧录，再整体重新上电进行相同速率的联合只读查询；混合速率阶段不作通信验收。

## 五轴 USB-CAN 稳定性验收

先核对五台 UID、APP 角色和版本，再对节点 3 至 7 各发送 70,000 次只读请求。
逐台应答和五台连续发送交替执行，覆盖设备身份、能力、启动状态和电机状态。
每笔从交给发送驱动计时，50 ms 截止，应用层重试次数为零。记录超时、收发错误、
协议或载荷不符、延迟及逐笔原始证据。采用固定样本量，要求整批和各节点首次失败率均低于
0.01%。同时计算二项模型单侧置信上限，五节点以 Bonferroni 校正控制总体 95% 置信水平。
出现成批故障时停止该轮，保存诊断，再用独立一轮复测。覆盖范围限于本次五轴静态台架。

### 复测条件和结果

USB-CAN 独占通道 0，ISO CAN FD+BRS，仲裁 500 kbit/s、数据 2 Mbit/s。节点 3 至 7
保持原有 APP 与 Loader。复测把收发进程调度优先级设为 AboveNormal，原始日志在整轮
收发结束后写盘，进程结束时恢复优先级。两项调整同时生效，各自贡献未单独测量。
用 `uv run python outputs/jlink-500k-2m-20261112/test_stability_prioritized.py` 在同一台架复现。

### 适配器时间戳对照

独立诊断用普通调度优先级，发送模式为正常发送并回显。以适配器的同一时钟匹配请求发送与
应答接收。72,270 对记录全部通过校验，适配器端往返中位数 1.1 ms，最慢 1.8 ms。
其中 9 笔主机往返超过 50 ms，最慢一笔主机读到时是 133.328 ms，适配器上为 1.0 ms。
该对照将长延迟定位到适配器所测总线往返之外，不能进一步区分 USB 驱动、操作系统调度和
应用执行的贡献。旧混速阶段节点 5 超时的 GET_INFO 序号 108 原始帧按原字节重放，100 次均成功。

这轮发送回显诊断中，SDK 另输出一次 `pkg head err! [0x00ef]`，含义未确认。
72,270 对收发均可关联，随后切回普通收发，五节点共 1,505 次查询全部通过。
