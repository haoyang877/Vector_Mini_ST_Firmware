# 电机通信与通用升级开发建议

> 当前设计入口：[1.2.3 CAN FD 统一协议评审稿](motor_protocol_v1.md)，仅采用 CAN FD 与公司统一帧框架，尚未完成固件实现。本文为历史设计参考，链路范围以当前设计稿为准。

> 2026-09-06 更新：用户已明确使用经典 CAN 加 29 位扩展 ID。本文早期 CAN FD 路线已由[电机通信与固件升级协议设计规范](motor_protocol_classic_can_v1.md)取代；后续按新规范的 CAN 紧凑实时帧和 J1939 TP 管理承载评审实施。

日期：2026-09-06。依据已读取的公司《通信协议设计 副本》及其关联《消息类型定义》，结合当前 STM32G431CB 工程。本文是开发顺序与验收建议，命令编号、ACK 细节等尚需协议评审，不是已实现功能。

## 1. 建议路线

先把统一协议核心做成可在 PC 验证的纯 C 库，再通过现有 CAN FD 接入电机状态机；随后实现独立于接口的升级核心和 Bootloader，最后验证第二种传输适配。公司统一帧格式是主干，USB、CAN、RS485、以太网是承载。当前板卡有什么硬件，就先实现相应驱动；业务接口从一开始保持可移植。

第一条真实链路选择 CAN FD，是因为当前工程已有该硬件和代码，不意味着升级绑定 CAN。第二条真实链路优先选硬件已具备的一种，例如 USB CDC 或接好收发器的 RS485；以太网可先在 PC/网关端验证 TCP 承载。USB CDC 与公司文档的 USB Bulk profile 不同，应明确登记为串口流式承载。

## 2. 写代码前补齐协议勘误与消息表

保留公司 16B 帧头、小端、magic=0xA55A、CRC8/CRC16 和 type 注册体系。先用一页勘误单定版下列事项，不必因此暂停独立的模块骨架、测试框架或 Flash 容量评估。

| 项目 | 建议决策，需评审确认 |
| --- | --- |
| ACK 位 | bit5 仅表示请求确认；bit4 区分请求/响应；响应不再请求 ACK，避免 ACK 循环 |
| ACK 业务含义 | 接受长操作与最终完成分开；Flash 成功必须对应写入及规定验证完成 |
| 帧头 CRC8 | 明确覆盖偏移 0～14，排除自身；按原文自定义参数生成黄金向量 |
| 帧尾 CRC16 | 明确覆盖完整 16B 头（含 CRC8）与 len 字节 payload，排除尾 CRC；核定自定义 0xBAAD 参数及 CRC 两字节顺序 |
| 帧头布局 | len 仍在偏移 10 时，用显式小端读写；不能把它当作自然对齐的 uint32 指针 |
| 分片会话 | 首版同一接收通道的 (src,dst,type) 只允许一条分片消息在途；绑定源连接、限制重组内存，明确首片重启、重复片和超时清理 |
| 序号语义 | 分清单帧事务序号和分片内片序；升级 payload 另有 session/request 标识，不能只用片序判定业务重复 |
| 长度上限 | uint32 len 是编码能力，不是 MCU 可以分配 4GiB；每消息类型及设备配置实际上限 |
| 流式承载 | 按 magic、头校验和 len 切帧，不能以一次串口 DMA/USB 回调/TCP recv 作为消息边界 |
| CAN 映射 | 明确标准/扩展 ID、优先级、路由、FD DLC 与填充；控制帧 payload ≤46B，禁止分片 |
| 控制时限 | 在线心跳与目标更新看门狗分离，超时动作和恢复条件由具体机械系统决定 |

保留原来的 CRC 多项式作为评审基线，不能因为其不属于常见命名算法就静默更换。为有效帧、空 payload、长 payload、错误长度、错误 CRC、首中尾片生成可复现的十六进制样例。

已读取关联消息表：0x0000 为测试指令；电机段 100～199 尚未填写具体定义；升级命令未见明确分配。不能把表格空白等同于可自行占用。电机消息在该段提交分配表；升级作为通用设备服务统一登记，用符号名开展开发，联调前固定编号。

## 3. 建议模块边界

```text
Shared/SysComm/
  wire_codec.c       固定偏移的小端编码、CRC8、CRC16
  stream_parser.c    485/UART/USB CDC/TCP 的流式拆帧
  fragmentation.c    按公司规则分片、重组、长度限制
  transaction.c      ACK、超时、重复请求、事务结果
  messages.h         type、payload 固定宽度字段与版本

Communication/Adapters/
  canfd_adapter.c    CAN ID/DLC/过滤/收发队列
  serial_adapter.c   串口收发、485 半双工调度
  tcp_adapter.c      在支持网络的平台提供连接与背压

Services/
  motor_service.c    消息 → 控制状态机与参数接口
  device_service.c   信息、能力、诊断
  update_service.c   镜像清单、写块、校验、激活状态机

Bootloader/
  boot_main.c        入口、恢复条件、应用验证与启动
  storage_port.c     Flash 擦写、边界、读回
  boot_metadata.c    启动记录与掉电恢复检查点

HostTools/
  protocol_cli       读取信息、控制联调、升级与故障注入
```

这是建议结构，不要求立即移动现有所有代码。先在现有 Communication 与 Foc 之间增加 motor_service 边界，再逐步迁移。

依赖规则：协议库不包含 STM32 HAL；升级核心不包含 can.h、串口句柄或 socket；仅通过完整消息和 peer_context 接收/应答，通过存储接口访问镜像槽。App 与 Bootloader 可复用同一协议源代码，但独立编译、独立资源配置，不依赖跳转前留在 RAM 中的协议状态。

头部采用 `read_le16/read_le32` 和 `write_le16/write_le32` 固定偏移访问，不直接把字节缓冲强转成 C 结构体。payload 可保持原文固定布局；对尺寸、offsetof、浮点表示和 ABI 做静态断言，跨平台优先逐字段编码。memcpy 本身不能解决大小端和结构体 padding 差异。

## 4. 按可验收结果推进

### 阶段 A：协议核心与 PC 对照工具

先实现公司帧的 encode/decode、CRC、流式拆帧与有界分片。PC 工具和 C 库共同读取一组黄金向量，至少一套结果由独立参考实现生成，避免相同错误互相验证。

验收：任意分割输入字节流、连续多帧、垃圾前缀、CRC 错、超大 len、缺片、重复片、尾片提前到达都能明确处理，不越界、不无限等待、不无限分配。PC 上运行内存检查工具；MCU 上测量最大栈与缓冲消耗。

### 阶段 B：只读板级链路

接入 CAN FD 适配，只实现 TEST、GET_INFO、GET_CAPABILITIES、GET_STATUS。先看见正确的节点身份、版本、计数、状态，再开放运动命令。

当前接收代码只准备 4B 数据缓冲，接长帧前必须改为容纳外设可交付的最大数据长度，再检查 DLC、帧类型、ID 与 HAL 返回值。中断只入队；主循环处理协议和服务。保留队列溢出、校验失败和重组超时计数。

验收：PC ↔ 板卡多次请求/应答稳定，错误帧不会改变电机状态；收发队列可测，旧协议与新协议入口明确分离。

### 阶段 C：最小电机业务闭环

首版完成以下业务即可：

- ENABLE / DISABLE：显式使能、失能；设置目标不能隐式使能。
- SET_MODE：电流、速度、位置；首版运行中禁止切换模式。
- SET_TARGET：明确单位、方向、坐标轴和限幅；输入整体校验后在控制周期边界应用。
- READ_STATUS：反馈实际状态、模式、目标已应用序号、位置/速度/Iq、故障。
- READ_PARAM / WRITE_PARAM / SAVE_PARAM：配置暂存与显式持久化分开。
- CLEAR_FAULT：仅原因消失后清除，清除后保持未使能。

后续版本再加阻抗、轨迹、多轴同步、辨识和批量配置。固件内部可以先维持现有 FOC 算法，通过统一接口封装；不要让协议层直接任意写 MotorControl。

验收：有效控制目标独立刷新运动看门狗；查询/心跳不掩盖目标停止。电机失联、重连、清故障后符合约定机械动作；无故障自动再使能。频率与总线负载以实际节点数和帧长测量，不能沿用原文未经核实的 <30% 结论。

### 阶段 D：先验证 Bootloader 布局与恢复入口

在实现下载流程之前，重新构建当前 App，核对 Flash、RAM、heap/stack、标定数据实际占用，明确 Boot 和 App 的链接区、向量表偏移及镜像打包规则。

当前 STM32G431CB 是 128KiB Flash，已有构建记录约 88KiB App；内置 A/B 不适合当前体量。先评估受保护 Boot＋单 App 恢复升级，不能先承诺坏版本自动回滚。之前 16KiB Boot/92KiB App 等布局只是预算草案，必须用实际编译结果证明能装下签名库和新协议。

验收：无需有效 App 也能进入维护接口；应用区无效时不跳转；Boot 与参数区不受普通升级擦写影响；首次安装 Boot 有明确工厂/维护刷写方案。

### 阶段 E：通用升级服务

统一业务流程：QUERY_CAPABILITIES → 提交镜像清单 → BEGIN → WRITE_DATA → FINALIZE → ACTIVATE → 查询启动结果。消息全部使用公司外层；session、request_id、image_id、offset、length、结果码和检查点都在 payload 中，不新增独立竞争外层。

首版一个块在途，支持同包重传、ACK 丢失与进度查询。块大小按 RAM、收发能力、Flash 对齐协商，例如 128/256B，不能写死为 CAN FD 的 46B；较长升级块按公司规则分片。先在 PC 用模拟存储实现同一业务状态机，再连接真实 Flash。

清单先核对产品、硬件、镜像大小和签名授权；写入只允许镜像区相对 offset，不提供任意地址擦写。块写入及规定读回完成后才确认成功；整镜像从存储重算摘要后才能激活。每片 CRC 不替代镜像哈希和来源验证。

next_offset 与掉电可恢复的 resume_offset 分开；检查点按安全的擦除单元推进，元数据使用可恢复提交。首版单 App 模式掉电后可重刷，不宣称能恢复到旧版本；有旧镜像存储后再做试启动/确认/回滚。

验收：写块重复不重复擦写；越界、错设备镜像、错摘要被拒绝；擦除、编程、元数据提交和激活各阶段随机断电后，设备进入有效 App 或可达 Boot，参数与标定不丢失。升级完成保持功率输出禁用。

### 阶段 F：第二接口与系统联调

用同一个固件包和相同业务测试，经 CAN FD 与第二个接口升级；更换的是传输适配器，升级核心源代码不随接口改变。RS485 明确主从轮询及 DE/RE 切换；TCP 按协议长度解字节流；UDP 和经典 CAN 通用升级承载另行制定，首版不必同时实现。

验收：所有接口对同一镜像得到相同结果；接口断开后重新建立合法会话才续传；跨接口同时写入只允许一个持有者。网关的分片/重组可改变承载形式，但不得翻译升级业务字段。

## 5. 每阶段交付物

| 交付物 | 用途 |
| --- | --- |
| 协议勘误单与消息注册表 | 消除原文歧义，避免团队各写一套解释 |
| 固定布局定义与黄金向量 | MCU、Linux、上位机逐字节对齐 |
| 纯 C 协议库＋PC 调试工具 | 在硬件前验证，在硬件上复现问题 |
| 电机命令状态转换表 | 明确接受条件、执行结果、失联动作 |
| Boot/App 分区及镜像清单规范 | 证明容量可行、启动与恢复可行 |
| 升级故障注入报告 | 证明断电、重传和失败后仍可维护 |
| 两种接口的一致性结果 | 证明升级业务确实不依赖通信接口 |

建议把“PC 与 MCU 用公司帧稳定完成信息查询，电机保持未使能”作为第一个开发里程碑。然后逐步开放运动控制和 Flash 写入，每次增加一种可观察、可验证的行为。
