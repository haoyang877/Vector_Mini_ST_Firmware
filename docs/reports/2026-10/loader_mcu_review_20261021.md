# Loader 多 MCU 改造复审与修复

日期：2026-10-21。复审对象：`faa76073` 的多目标边界改造；原始实现参考 `f199f7d4`。
修复提交：`2bb91c3f`。吸收重构主线 `31941dbc` 后的验证提交：`e95b4d05`。
本轮只做代码、构建及离线模型检查，没有连接 J-Link、CAN 或电机。

## 结论

没有发现这次改造使 G431 原有升级、故障恢复或参数保留逻辑退化。
发现并修复了两类面向后续 MCU 适配的遗漏：APP 工程没有完整采用新目标，
以及构建检查没有保证实际工程与目标清单一致。此前 G431 默认配置恰好与模板一致，
所以这两类问题没有改变其已构建的固件。

修复前后用同一份 G431 源码、目标和升级 token 构建，Loader 与 APP 的 BIN 均逐字节一致。
这说明本轮工具修复没有改变运行代码；不等于多 MCU 改造前后的所有 Loader 二进制完全相同。
最初的职责移动曾使 Loader 增加 28 字节，已在[前次记录](loader_mcu_boundaries_20261021.md)说明。

## 发现并修复的问题

| 问题 | 影响 | 修复 |
| --- | --- | --- |
| APP 生成器继承模板设备名、芯片宏；复制到其他目录后路径仍相对于旧目录 | 新目标可能编译成旧 MCU，或找不到源文件 | 设备名和编译宏来自所选目标；源文件和头文件路径重新定位；只保留一个目标 |
| 配套构建只核对目标头，未核对实际工程和链接脚本；Qt 仅检查选择头是否存在 | 使用旧工程或旧头时，目标 JSON 可能与真正编译内容不一致 | 配套构建共用生成器只读重算全部生成输入，不一致则在调用编译器前失败；Qt 配置同时检查选择头和常量 |

APP 专用编译宏写入 `build.app_defines`，没有将 Loader 宏直接套用到 APP。
G431 继续保留原来的 6 毫欧采样电阻设置。协议字段、参数格式、固件版本和 Flash/RAM 分区未变。
新增项只是构建元数据，不改变旧升级包的 MCU、产品、布局或参数兼容判定。

## G431 行为核对

| 检查范围 | 结果与边界 |
| --- | --- |
| 正常升级 | 主机到真实 Loader 内核的下载、读回、校验、激活和发送完成处理通过；丢失回复、重发及旧会话拒绝保持原行为 |
| 升级中断或掉电 | 原生模型覆盖下载各写入边界，以及激活、首次启动和确认标记的半写；不完整镜像不能启动，可重新下载 |
| 故障 APP | 实际构建镜像接入启动模型；看门狗复位驻留 Loader，已试运行但未确认的 APP 不再次启动，已确认镜像可正常启动 |
| APP 交接 | 有效软件复位与 ENTER 邮箱才强制驻留；普通冷启动不会误用邮箱；启动窗口和发现请求逻辑保持原行为 |
| 参数与 CAN ID | 真实产品解析接入启动模型；正常参数使用原节点，空白、格式损坏和读取失败保留救援节点；旧参数 schema 兼容测试通过 |
| 参数和 SN 保留 | 实际 G431 平台入口只能擦写 APP；遍历擦除整个 APP、写首尾及失败返回后，Loader、参数和身份区逐字节不变；启动路径也不改写参数 |
| 安全输出 | 板级关闭状态判断与移动前函数体一致；输出未关闭时，真实 Flash 入口拒绝写入；未改变故障停留策略 |

参数解析仍只提取可用于通信的节点，不替 APP 执行完整参数 CRC 和配置有效性检查。
故障恢复仍为单 APP 槽重新下载，不提供被擦除旧 APP 的自动回滚。
实际掉电、电气信号、总线恢复时间和连续实机升级不在本轮验证范围。
