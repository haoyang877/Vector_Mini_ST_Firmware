# 文档维护规则

## 保留范围

docs只长期保留当前设计、接口契约、兼容格式、硬件设计输入及必要工程/产品说明。
总入口按10组设计组织。一个事实由所属主题维护，其他页面只引用。
不按每次实现、调试、测试或发布新增阶段文档，不保留历史草稿、过程报告和完成计划目录。

## 设计更新

变更先在所属设计说明问题、输入输出、状态所有者、执行上下文、失败处理和验收条件。
实现后回填真实行为；未实现部分明确标识，不以设想覆盖当前契约。
协议/参数ABI变更同步版本化说明、黄金向量和兼容策略。
仍有消费者的旧协议/存储格式是设计契约，不按日期删除。

显著工作需要的基线、计划、对照、检查日志和临时报告写到忽略的outputs。
完成后仅将稳定设计结论合入主文档。Git保存演变历史，不在当前文档树复制一套旧稿。
既有失败和未测项在当次验证证据中说明；设计页只保存仍有效的约束与验收要求。

## 合并与删除

先提取有效的字段、边界、公式和设计理由，再删除重复页或过程记录。
同步所有索引、相对路径和锚点；不留跳转占位，不把已删除报告链接伪装成设计依据。
保留当前源码、工程和原始实验数据；文档整理不顺带修改固件。

## 检查

运行文档链接检查、相应级别verify以及git diff --check。
纯文档至少quick；修改文档检查器等harness规则时使用PR级。
检查器要求architecture、protocols、guides、hardware入口且检查本地Markdown目标，
人工仍须核对语义、重复和标题锚点。失败不得通过削弱断言、伪造证据或扩大豁免消除。
