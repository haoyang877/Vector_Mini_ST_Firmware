# 文档维护规则

## 当前约定与事实来源

docs/README.md为总入口，各主题README列出当前有效说明。
架构和公开行为变化时，在同一次变更中同步所属主题，避免再建一份重复总览。
参数/协议以版本化契约和黄金向量维护；目标版本、分区、ABI的配置来源是shared/targets，
支持能力由产品注册表和真实所有者决定。文档或枚举不能替代代码接线和设备验收。

## 新增与更新

先搜索已有主题；能补充现行说明时直接更新，不按每次聊天再建“最新版”。
显著工程工作在plans/active创建日期/版本计划，写目标、当前基线、不变项、验收、回退和证据。
阶段日志放计划或reports；生成日志、图片、二进制、manifest放忽略的outputs。
现行文档注明核对日期、适用实现和实际来源；未实现/未测项明确登记。

## 完成、归档与合并

原计划范围结束且正文有结果时移至plans/completed；只完成离线工作不等于硬件或release通过。
被替代、撤回、依赖已删除实现或无法再沿原基线执行的材料移至docs/archive，
写明原因及现行入口。归档不代表任务全部完成；仍有效的缺口转入现行计划或限制表。
合并重复主题时提取仍有效的字段、边界和流程到唯一现行页，旧稿作为历史保留。
旧协议/参数若仍有兼容读取或回归消费者，明确标为兼容资料并保持向量稳定，不按日期直接删除。
历史报告保留成功、失败、哈希与未测边界，不因新结果覆盖原始结论。

移动前检查引用。移动后重算相对链接，历史记录引用历史基线，当前说明指向当前主题。
不要在原路径留大量跳转占位页，也不要借文档整理改动固件或测试实现。

## 检查与提交

```text
uv run python tools/harness/check_docs.py
uv run python tools/run.py verify --profile quick
git diff --check
```

已有check_docs检查目录入口、Markdown本地目标和少量已知过时文本，
不判断源码语义、文档重复、标题锚点或计划状态；这些须人工对照实际实现。
若修改harness规则需PR档；本文规定维护流程，不新增检查器或豁免已有门禁。
所有长期文档随Git版本管理；工作树文档整理未提交前，不宣称其他分支已同步。
