# 删除旧标准 CAN 协议并收口 CAN FD

## 目标

将电机固件的通信入口、调度、命令路由和状态反馈完全收口到 `yg_protocol` CAN FD
协议。旧的 11 位标准 CAN 参数帧、48 字节状态流、旧心跳看门狗和旧波特率切换入口
不再作为产品协议保留。

CAN FD 线路基线保持为：仲裁段 1 Mbit/s、数据段 5 Mbit/s、29 位扩展 ID、FD+BRS。
协议层使用公司帧头、CRC、请求/回复、分片和序列号定义；通信业务不直接依赖 HAL。

## 当前基线

- 当前固件仍存在两条入口：旧标准 CAN 路径和 `yg_protocol` CAN FD 路径。
- `YgProtocolLink` 已能离线编解码，并已在目标板上完成 GET_CAPS、GET_INFO 和
  GET_MOTOR_STATE 的只读冒烟；GET_MOTOR_STATE 在状态源尚未绑定时返回 BUSY。
- 最近一次 release 证据：
  `outputs/runs/20260922T071436899469Z-ef007a0a/summary.json`。
- 最近一次目标板验证的固件、适配器和帧记录位于 `outputs/bench/`，这些文件是证据，
  不是源码输入。

## 不变项

- 电机控制算法、功率级安全关断、参数 Flash ABI 和现有物理量单位保持不变。
- CAN FD 的 1M/5M 位时序、29 位扩展帧、CRC 和字节序以现有公司协议文档与黄金向量为准。
- 应用层不包含 STM32 HAL 类型；硬件差异只存在于 `platform/api` 和端口实现。
- 普通验证不连接硬件、不下载固件、不驱动电机。

## 分阶段实施

### 阶段 1：建立唯一入口

1. 新增 CAN FD 专用初始化、RX ISR 和后台服务接口。
2. RX ISR 只接收 FD 扩展帧并交给 `YgProtocolLink`，删除标准帧分支。
3. `Board_Init`、主循环和监督任务只调用新接口；移除旧 `CAN_Service`、
   `CAN_BaudRateSwitching` 和 `CAN_DisConnect_Handle` 调度。
4. 参数服务的节点身份桥改为协议节点身份桥，暂保留同一参数存储和单位。

阶段 1 的验收是全量编译、离线测试通过，并且源码中不存在旧标准帧 RX/TX 的可达入口。

### 阶段 2：迁移业务命令

1. 将模式、位置/速度/电流、停止/禁用、参数读写、标定和零位命令注册到
   `yg_protocol_motor_service_t`。
2. 将状态、故障、位置、速度、扭矩、电压、电流、温度和控制模式统一通过
   `yg_protocol_motor_status_source_t` 输出。
3. 所有命令都返回协议回复；业务失败与线路失败分别编码。
4. 对 1 kHz 多轴控制采用有界队列、时间戳和序列号，不能在 ISR 中执行电机业务。

### 阶段 3：删除旧实现

删除旧协议专属的 `interface_can.*`、`can_transport.*`、旧参数绑定、旧查询、旧状态流
编码器及其 Keil 工程组、测试和主机镜像。可复用的电机状态采样逻辑迁移到新的状态源
适配器后再删除旧文件，避免删除业务能力。

### 阶段 4：验证和硬件回归

1. PR 验证：格式、静态检查、单元测试、协议黄金向量、工程编译。
2. Release 验证：生成并记录 AXF/HEX/MAP 哈希及内存占用。
3. 无动力台架：GET_CAPS、GET_INFO、状态查询、STOP、DISABLE、参数读写和错误回复。
4. 连接整机前确认 PWM 已关闭；硬件证据记录 Node ID、位时序、原始帧和固件哈希。

## 验收条件

- 源码和 Keil 工程中不存在旧标准 CAN 命令的编译入口。
- 所有 CAN 收发都经过 `yg_protocol`，平台层只提供 CAN FD 能力。
- 旧协议的命令编号不会被新协议复用或隐式兼容。
- 新协议业务命令有明确的请求、回复、超时和错误语义。
- 无新增动态内存、无阻塞等待；ISR 和后台服务均有明确的处理上限。
- PR/release/硬件证据均来自当前提交，不复用旧输出声称验证通过。

## 回滚策略

每个阶段单独提交。若新业务命令尚未完成，允许回滚到上一阶段的 CAN FD-only 版本；
不允许通过恢复旧标准 CAN 入口来掩盖新协议缺失。任何协议 ABI 变化必须同步更新
版本化文档、黄金向量、主机镜像和测试。
