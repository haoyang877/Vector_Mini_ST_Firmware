# YG2026-ESC 固件发布规范

文档版本：v1.0.0

制定日期：2026-09-17
适用项目：`YG2026-ESC-APP`、`YG2026-ESC-LOADER`

## 1. 适用范围

本规范统一电机驱动 APP 和通用 MCU Loader 的固件命名、版本管理、发布检查及归档要求。

发布分支仅保留 **release、debug、factory**。取消 `product` 分类，量产交付使用经验证的 `release` 固件；工厂测试、标定专用固件使用 `factory`。

本文定义后续发布要求，不代表现有代码已实现全部发布工具、镜像元数据或验证流程。

## 2. 固件命名格式

```text
项目名-芯片型号-分支名-版本号-发布日期.扩展名
```

两个项目使用固定前缀：

```text
YG2026-ESC-APP-芯片型号-分支名-vX.Y.Z-YYYYMMDD.扩展名
YG2026-ESC-LOADER-芯片型号-分支名-vX.Y.Z-YYYYMMDD.扩展名
```

| 字段 | 规则 | 示例 |
| --- | --- | --- |
| 项目名 | 仅允许两个固定名称，保持大写 | `YG2026-ESC-APP` / `YG2026-ESC-LOADER` |
| 芯片型号 | 使用目标配置登记的准确型号；大写字母和数字，不含空格或连字符 | `STM32G431CB` |
| 分支名 | 仅允许 `release`、`debug`、`factory`，小写 | `release` |
| 版本号 | 小写 `v` 加三段非负整数；数字无多余前导零 | `v1.2.0` |
| 发布日期 | `YYYYMMDD`，合法日期；按北京时间 UTC+08:00 的实际发布日期填写 | `20260917` |
| 扩展名 | 小写，与文件真实格式一致 | `.bin`、`.hex`、`.elf`、`.axf` |

项目名自身包含连字符，解析时必须识别固定前缀或使用完整正则，不能按固定五段简单切分。

不使用空格、中文、`final`、`new`、`最新版`、`修改版`、`(1)` 或任意附加后缀。构建时间、Git 信息、硬件版本等放入发布清单，不随意改变文件名结构。

芯片字段不能只写 `STM32`、`G4` 等系列简称。相同芯片的不同板卡通过清单中的 `target_profile`、硬件兼容标识进一步区分，文件名本身不构成硬件兼容性证明。

### 2.1 分支定义

| 分支 | 使用场景 | 发布条件 |
| --- | --- | --- |
| `release` | 正式功能发布、量产安装和客户升级 | 完成目标平台的功能、保护、兼容性及升级验证 |
| `debug` | 开发联调、问题定位、工程试验 | 可启用诊断和额外观测，必须记录已知限制；不作为默认量产镜像 |
| `factory` | 产线测试、标定、硬件检查和维护作业 | 验证对应工厂流程，并说明作业结束后保留该固件还是切换到 release |

文件名中的“分支名”表示固件发布类别，不要求实际 Git 分支只有这三个名称。实际 Git 分支和完整 commit 写入发布清单。

APP 和 LOADER 都使用此枚举；只发布确有用途的构建类别，不强制为每个版本生成全部三类。

### 2.2 命名示例

```text
YG2026-ESC-APP-STM32G431CB-release-v1.2.0-20260917.bin
YG2026-ESC-APP-STM32G431CB-debug-v1.2.1-20260917.hex
YG2026-ESC-APP-STM32G431CB-factory-v1.0.0-20260917.bin

YG2026-ESC-LOADER-STM32G431CB-release-v1.0.0-20260917.bin
YG2026-ESC-LOADER-STM32G431CB-debug-v1.0.1-20260917.axf
YG2026-ESC-LOADER-STM32G431CB-factory-v1.0.0-20260917.hex
```

以上为格式示例，不表示这些版本或构建产物已经发布。

## 3. 版本号管理

采用 `vX.Y.Z`：

| 位 | 名称 | 递增条件 | 示例 |
| --- | --- | --- | --- |
| X | 主版本 | 引入不兼容的协议、参数 ABI、布局或升级契约变更 | `v1.5.3 → v2.0.0` |
| Y | 次版本 | 新增功能，保持对该发布线已有接口的兼容性 | `v1.2.3 → v1.3.0` |
| Z | 修订号 | 修复问题、兼容性优化，或需要独立发布标识的构建配置调整 | `v1.2.3 → v1.2.4` |

规则：

1. 主版本递增时，次版本和修订号归零；次版本递增时，修订号归零。
2. APP 与 LOADER 独立维护版本号，通过清单记录兼容关系，不要求版本相同。
3. 同一组件、芯片、发布类别和版本只对应一套已发布构建配置。不同板卡或链路配置产生不同镜像时，在当前五要素命名规则下分配不同版本号，并登记 `target_profile`。
4. 已发布内容变化必须递增版本号；只修改日期不能替代版本递增。同一天多次对外发布也按此处理。
5. 同一构建导出的 BIN、HEX、ELF/AXF 可以使用相同主文件名和不同扩展名；重新构建的不同内容不得覆盖原文件。
6. debug 验证通过后，使用 release 配置重新构建和验证，不能只改文件名宣称已完成正式发布。
7. 固件可查询的版本信息、镜像元数据、文件名和发布清单必须一致；版本信息生成方式在构建阶段统一管理。

版本号表示发布演进，不能单独证明可升级或可降级。是否兼容仍需核对布局、协议、参数 ABI 和硬件标识。

## 4. 构建与镜像约定

每次发布明确以下构建输入：源码 commit、target profile、编译器版本、构建目标、优化选项及影响行为的宏定义。

- release 和 factory 使用可追溯的已提交源码进行干净构建，归档实际构建命令或工程目标。
- debug 如确需包含未提交修改，清单标记 `dirty=true`，同时归档相应源码快照/补丁；不能仅记录一个不包含实际修改的 commit。
- BIN 为原始字节镜像，烧写基址必须由清单和布局契约提供；HEX 的地址范围同样需要检查。
- ELF/AXF 和 map 用于调试与追溯，归档时注明用途，不默认当作在线升级输入。
- APP 和 LOADER 分别构建、分别发布。现有规范不将两者拼接后仍命名为 APP 或 LOADER；需要整机部署包时用独立包清单描述各组件和地址。
- 芯片相同但布局不同的镜像不能互换。升级工具不得仅凭文件名或文件大小判断是否允许写入。

针对当前 D-loader 设计：设备侧移除 USB；Loader 按目标支持 CAN-FD/UART，优先交付 CAN-FD。清单必须列出该构建实际启用并验证的链路，不能将框架规划能力标为已实现能力。

## 5. 发布清单

每个发布包附带机器可读的 `manifest.json`。首版字段要求如下；具体序列化由发布工具统一生成。

| 字段 | 内容 |
| --- | --- |
| `manifest_version` | 清单格式版本 |
| `project` / `component` | 固定项目名及 `APP` / `LOADER` |
| `mcu` / `target_profile` | 芯片型号及准确构建目标 |
| `branch` / `version` / `release_date` | 与文件名一致；日期统一为 `YYYYMMDD` |
| `hardware_compat_id` / `layout_id` | 硬件兼容范围与存储布局标识 |
| `git_commit` / `git_branch` / `dirty` | 完整源码版本及构建时工作区状态 |
| `toolchain` / `build_target` / `build_options` | 可复现的构建信息 |
| `enabled_transports` | 固件实际启用的升级链路，如 `CAN_FD`、`UART` |
| `protocol_version` | 该组件实际使用的通信/升级协议版本 |
| `compatible_loader_versions` | APP 接受的 Loader 版本范围；不适用时明确标注 |
| `param_abi_id` / `param_schema_range` | 参数布局和可接受 schema 范围；不适用时明确标注 |
| `image` | 编程基址、实际传输长度、填充规则、CRC32 算法及校验值 |
| `artifacts` | 每个产物的准确文件名、字节数、用途、SHA-256 |
| `validation` | 已执行测试、结果及对应报告路径 |

SHA-256 针对归档文件本身；镜像 CRC 针对升级实际传输的字节序列。若 BIN 补齐、HEX 转换或裁剪导致内容变化，应先生成最终升级镜像，再计算长度与 CRC，并将该最终文件作为独立产物登记。不能把 HEX 文本文件的 CRC 当作 APP 镜像 CRC。

校验和用于完整性和追溯，不等同于固件签名。没有实际生成或验证的字段不得填写虚构值，也不能将示例值带入正式包。

## 6. 发布验证要求

所有发布类别都执行命名、构建、范围和校验一致性检查；功能验证深度按类别及变更影响记录。

| 检查项 | 要求 |
| --- | --- |
| 命名一致性 | 文件名合法，且项目、芯片、分支、版本、日期与清单一致 |
| 构建结果 | 无编译/链接错误；新增警告处理完毕，遗留例外有明确记录 |
| Flash/RAM | 实际加载范围、静态 RAM、堆栈和保留区满足目标配置 |
| 目标兼容 | 核对 MCU、板卡、布局、APP/Loader 协议及参数 ABI |
| 固件完整性 | 最终镜像长度、CRC、文件 SHA-256 校验一致 |
| 基本功能 | 启动、通信、版本查询及本次变更相关功能通过 |
| APP 保护 | 电机启停、输出安全态及相关故障保护按变更范围回归 |
| 升级路径 | 对实际发布链路验证正常升级、超时恢复及参数区保留 |
| 恢复能力 | Loader、布局或升级机制变更时补断电/坏镜像/坏 APP 救援验证；未测项目不得记为通过 |

release 面向正式交付；factory 验证相应产线/标定操作；debug 必须列明尚未通过或未执行的验证和已知问题。静态检查、离线模拟、软件复位和真实硬件断电试验分别记录，不相互替代。

新 APP 的试运行确认和看门狗恢复目前属于设计要求，相关机制未实现或未验证时，在发布记录中明确说明。

## 7. 发布包及归档结构

使用不含扩展名的固件主文件名作为发布目录名：

```text
YG2026-ESC-APP-STM32G431CB-release-v1.2.0-20260917/
├── YG2026-ESC-APP-STM32G431CB-release-v1.2.0-20260917.bin
├── YG2026-ESC-APP-STM32G431CB-release-v1.2.0-20260917.hex
├── manifest.json
├── release_notes.md
├── checksums.sha256
├── build/
│   ├── build.log
│   └── build_config.json
├── symbols/
│   ├── YG2026-ESC-APP-STM32G431CB-release-v1.2.0-20260917.axf
│   └── YG2026-ESC-APP-STM32G431CB-release-v1.2.0-20260917.map
└── validation/
    └── report.md
```

BIN/HEX 按用途提供，符号产物按工具链使用 ELF 或 AXF，不要求无用途的重复导出。对外部署包可只含所需镜像、清单和说明，完整构建、符号和验证证据保存在内部归档。

如压缩交付，压缩包名采用相同主文件名加 `.zip`。`checksums.sha256` 列出最终交付镜像和清单等文件的哈希，不列自身；归档后不再修改已计算校验值的文件。

发布说明至少记录：新增/修复内容、适用硬件、实际支持链路、兼容版本、参数迁移影响、已知问题、验证范围及升级/恢复方法。

## 8. 发布操作流程

```text
确定组件 / MCU / target profile / 发布类别
    ↓
冻结源码和版本号
    ↓
干净构建并导出最终镜像
    ↓
检查布局、容量、参数与协议兼容性
    ↓
执行规定验证并归档结果
    ↓
生成清单、发布说明及校验文件
    ↓
核对命名和包内一致性
    ↓
归档并交付，保留原发布包
```

已发布文件不得被不同内容覆盖。发现问题时保留原包及其哈希，标记为撤回并发布新版本，记录替代关系；不把原问题包重命名成新版本继续使用。

## 9. 自动命名校验

固件文件名采用以下正则进行结构校验：

```regex
\AYG2026-ESC-(APP|LOADER)-([A-Z0-9]+)-(release|debug|factory)-v(0|[1-9][0-9]*)\.(0|[1-9][0-9]*)\.(0|[1-9][0-9]*)-([0-9]{8})\.(bin|hex|elf|axf)\Z
```

该表达式采用 Python 正则语法；其他工具按对应语法实现完整字符串匹配。额外检查：

- 日期能按 `YYYYMMDD` 解析为真实日历日期。
- MCU 和 target profile 在目标注册表中存在。
- 文件名字段与清单和镜像元数据一致。
- 同名发布产物不与归档的已有内容冲突。

`product` 不是合法分支。旧历史产物保留原始归档和校验信息，不直接重命名为 release；正式迁移时按 release 配置和本规范重新发布。
