# yg_protocol 业务重构实施方案 v0.1

日期：2026-09-23。状态：**历史方案；电机控制部分已由[简化决策](2026-09-23-yg-protocol-simplification.md)替代，不按本计划直接修改业务代码**。本计划接续[业务 Type 分配提案 v0.3](../../protocols/yg_protocol_business_type_allocation_v0_3.md)，记录当时的实现顺序、接口和验收。执行时每阶段单独提交；任何线上 ABI 变动同时提交版本化协议文档、黄金向量、主机镜像和兼容说明。

## 1. 目标与现状

目标是让公司统一帧和 CAN FD 成为电机控制、反馈、参数、标定、同步和升级的实际业务入口。业务逻辑只接收经验证的值对象；电机运行所有者负责模式、目标、功率和故障状态，参数所有者负责参数与 Flash，Loader 负责镜像写入/验证。CAN ID 只管仲裁和寻址，应用头 `type` 只管业务路由。

代码基线 `6089a5a1`：

- `yg_protocol_link` 已注册 1/2/108/110/111；1、2、108 有只读回复，110/111 未绑定执行服务，返回 UNSUPPORTED。124 只有描述符/编码能力，没有周期发送。
- `Board_Init` 初始化链路并绑定只读状态源。FDCAN 中断只入队，主循环刷新快照并调用运行时服务。当前 RX 8 帧、TX 40 帧；没有实时优先队列或固定 1 kHz 调度保证。
- 状态适配器目前把 `last_applied_sequence` 固定为 0、`target_applied=false`；状态中的温度来自 MCU，Iq 不是经过标定的机械力矩。
- STOP/DISABLE 的平台无关停机服务和电机适配器已有离线代码，但没有与 `FocRunState` 所有者绑定。参数 READ 适配器已有离线代码，但还未成为运行路由；WRITE/SAVE 未实现。Loader、主机应用和共享升级契约未形成可运行升级闭环。
- 旧标准 CAN 协议已删除，不列入迁移或回退路径。普通验证不得下载固件或驱动电机。

## 2. 在动代码前先冻结的决定

| 决定 | 推荐值 | 未冻结的影响 |
| --- | --- | --- |
| 业务 Type | 按 v0.3 先申请登记，保留已注册 1/2/108/110/111；50～59、116、125、193 为首批重点 | 两套主机表会把同一编号解释为不同命令 |
| 主控 Node ID | 推荐遵循飞书原文：RV1126B=`0x02`，`0x01` 为上层 MT6897；电机 `0x03～0x07` | 现有项目确认记录把主站写作 `0x01`，必须统一后才能冻结地址/权限黄金向量 |
| 应答语义 | 管理、参数、标定、升级请求用同 type 业务回复；周期目标由对应反馈回显已应用序号，失败另报错误 | 逐帧额外 ACK 会使 5 轴 1 kHz 总线预算失效 |
| 实时缺包策略 | 目标只在显式短有效期内可用；过期由电机所有者停机，绝不使用 1 s 事务超时作为运动保护 | 失联时可能长期保持旧目标 |
| 单路容量 | 首轮在 1M/5M 单路实测；若最坏截止时间与余量不足，再评估双路 3+2 或经确认降频 | 单路五轴 1 kHz 模型已占约 84% 周期，不可预先承诺硬实时 |
| 升级契约 | 在 Loader 阶段另冻结镜像布局、摘要/签名、最大块和 App/Loader 交接 | 没有镜像身份与校验定义就不能安全实现 UPDATE_WRITE/ACTIVATE |

飞书原文只确认 0～99 通用、100～199 电机段；具体业务 Type 和升级段尚未正式登记。若公司登记调整编号，先更新 v0.3 和黄金向量，再进行对应服务开发。flags ACK/RESPONSE 的原文歧义也应在第一批向量中裁决。以上决策是方案评审门槛，不要求一次批准所有后期功能；但每个阶段动代码前，其涉及的字段必须定版。

## 3. 目标接口与程序流

```text
FDCAN RX ISR → comm_hw 完整帧 → yg_protocol_link RX 队列
           → 公司帧/CRC/地址/长度校验 → registry/router
           → 各业务 codec 转成明确单位的值对象
           → 应用组合层调用电机/参数/任务/升级所有者窄接口
           → 业务结果编码 → yg_protocol_link TX 调度 → comm_hw CAN FD

2 kHz 电机状态机 / 20 kHz 快环 → 唯一所有者应用命令并产生快照
                                   → 应用状态适配器 → 108/124/125/126
```

- `communication/protocol`：纯 codec、Type 登记、字段和结果映射；不得包含 HAL 或可变电机全局量。
- `communication/can`：CAN FD 承载、队列、优先级和路由；不能直接写 `MotorControl`、Flash 或 PWM。
- `app`：组合、权限检查、与电机所有者交接、状态快照；由现有生命周期状态机决定使能/停机/故障。
- `services/parameters`：参数描述符、范围和运行态写入/保存策略；存储与版本校验归现有参数服务。
- `loader` 与 `shared`：镜像会话、块写入、整包校验、启动结果和 App/Loader 共享线上契约，独立构建。
- `host_app`：相同 codec/向量、请求去重和反馈周期关联；不在主机私自重定义单位或 Type。

业务对象原则上通过小型命令邮箱或显式请求 API 交给电机所有者。收包前台不得直接改模式/目标；控制周期取走命令、验证当前状态并记录实际应用序号。回复中的 ACCEPTED 只说明受理；108/124/125 才能报告应用结果和物理反馈。避免在同一状态上建立第二套“通信模式状态机”。

## 4. 分阶段交付

| 阶段 | 实现范围与主要文件 | 可独立验收的交付 | 规模 |
| --- | --- | --- | --- |
| A. 冻结契约 | v0.3 Type 表、`yg_protocol_wire_types`/registry、payload 文档、主机/固件黄金向量 | Type 无冲突；权限、单播/广播、回复/重试/错误含义有向量；GET_CAPS 只声明已实现能力 | 中 |
| B. 安全入口 | `yg_protocol_motor_adapter`、`motor_stop_service`、`FocRunState`、`board_config` 组合 | 110/111 真正请求所有者停机；未验证功率关闭绝不回 OK；重复命令幂等；断线与故障保持安全 | 中 |
| C. 单轴控制 | 4/5 控制会话、101/106/107/116、应用命令邮箱、状态机消费点 | 模式与目标范围/单位检查；目标不隐式使能；应用序号随实际控制周期更新；单轴 CAN FD 闭环 | 大 |
| D. 单轴反馈 | 124 周期快照、109 报告配置、126 事件、108 完整状态 | 周期发送从确定的采样/调度点触发；位置/速度/Iq 同快照；故障/状态可查询；无伪造温度/力矩 | 中 |
| E. 参数和任务 | 120～123、160～165，现有参数与标定/辨识服务 | READ/WRITE/SAVE 的 revision 与权限；带 `task_kind` 和参数的异步任务，结果/取消/应用可查询 | 大 |
| F. 五轴同步 | 180/181/186、190～194、125，主机组控制与实时队列 | 先单轴→两轴→五轴；未来执行时刻、有界 FIFO、固定采样/回传相位、欠载停机；1 kHz 实机证据 | 很大 |
| G. 升级 | 50～59、`shared` 契约、Loader、APP 交接、host 工具 | 完整升级、失败恢复、镜像校验、重启结果；电机输出已关断且升级流量不挤占实时控制 | 很大 |

每阶段结束更新登记表状态和能力位，移除无真实调用者的临时代码；不一次性注册 65 个候选 Type。B 完成前不启用远程使能，D/F 的周期报告不能靠主循环“尽快调用”来保证 1 kHz。E 与 F 可在 A～D 接口冻结后由不同模块并行开发；G 与 Loader/共享镜像契约可单独开发，但最终必须进行整机集成。若阶段 B 的 STOP 请求无法可靠确认物理关断，应停在 B 修正，不继续开放阶段 C。

## 5. 每阶段固定验收门槛

1. **协议正确性**：每个新增 Type 有正常、拒绝、重复、坏 CRC、长度错误、超范围、错节点/广播、序号回绕及小端黄金向量；大管理消息另测分片中断和重试。
2. **电机安全**：状态机只有一个写者；故障与 STOP 可到达功率禁止；失败不回 OK；不能通过查询/心跳/重复目标刷新运动新鲜度。台架失败后先确认 STOP/输出关闭，不能自动恢复试验。
3. **资源与时序**：固定 RAM/Flash、队列占用与最坏服务时间；实时命令不分片、不阻塞、不做 Flash；TX 按停止/目标/反馈/管理排序，过期周期帧不得积压发送。
4. **验证**：固件、协议或参数改动至少通过 `verify --profile pr`；Keil/硬件/发布相关阶段通过 release 档并记录当前提交的 `summary.json` 与 AXF/HEX/MAP 哈希。硬件测试使用显式 bench 场景，记录原始帧、节点、1M/5M 位时序和停机证据。
5. **完成判据**：B 为无动力 STOP/DISABLE 实机闭环；C/D 为单轴位置目标和状态反馈闭环；F 为至少五轴每轴 1 kHz、每周期目标应用与反馈完整率、总线余量和故障注入实测；G 为 Loader 真机升级及失败恢复。若 F 单路达不到截止时间，只报告实测并按已裁决的拓扑/频率方案继续，不降低指标后声称原目标达成。

## 6. 提交、回退与边界

推荐每个阶段分为“契约/向量 → 纯协议服务 → 所有者适配 → 工程接线 → 测试/文档”几个可审查提交。阶段验收未通过时回退该阶段的路由绑定或功能开关，保留上一阶段已验证的 CAN FD 唯一入口；不恢复旧标准 CAN 协议。涉及公共 payload、Type、错误码和单位的修改必须整体回退，不能只回退固件而留下主机或文档不一致。

本方案的下一步是评审第 2 节决定和阶段 B～D 的最小业务闭环。评审通过后先实施 A 与 B；阶段 E、F、G 再按各自的硬件和 Loader 条件单独验收。
