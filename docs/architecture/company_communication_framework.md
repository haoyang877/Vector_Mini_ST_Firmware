# 公司通信协议框架梳理

日期：2026-09-20。状态：框架澄清稿，尚未改变固件行为。

本文把三个来源分开，避免把设计建议误认为公司规范：

1. **ChatGPT 会话《通信协议框架设计》**：提出硬件无关的应用协议、服务层、编码层、传输抽象层
   和链路适配层，是架构设计输入。
2. **飞书《通信协议设计 副本》**：规定统一帧、字段、节点和传输适配方向，是公司协议基线；其中
   仍有若干冲突和空白需要公司裁决。
3. **当前固件代码**：仍运行旧的 11 位标准 CAN 参数协议和 48 字节状态流，不能当作新协议实现。

## 1. 先理解“协议”到底分几层

```text
电机业务对象
  ├─ 控制命令：使能、停机、模式、位置/速度/力矩/电压目标
  ├─ 状态对象：位置、速度、电流/力矩、模式、故障、温度、电压
  ├─ 参数对象：读取、修改、保存、回滚、默认值
  ├─ 任务对象：辨识、标定、诊断、实验
  └─ 升级对象：镜像、分块、校验、激活、回滚
        ↓
应用服务层
  ├─ 周期控制服务
  ├─ 周期状态服务
  ├─ 参数服务
  ├─ 任务/诊断服务
  └─ 固件升级服务
        ↓
统一应用消息层
  ├─ version / flags
  ├─ src_id / dst_id
  ├─ type / sequence
  ├─ payload length / payload
  └─ 应用层完整性校验
        ↓
传输抽象层
  ├─ 单帧承载
  ├─ 分片与重组
  ├─ 序号、超时、重传、ACK
  └─ 广播、单播、优先级
        ↓
链路适配层
  ├─ CAN FD：29 位 ID、DLC、FD、BRS、仲裁
  ├─ RS485：地址、主从轮询、字节流分帧
  └─ 以太网：TCP/UDP/其他承载的收发与会话
        ↓
物理层
```

关键边界是：**电机服务只处理业务对象，统一消息层只处理应用帧，链路适配层只处理承载，不让
CAN ID 或 HAL 类型进入电机控制算法。**

## 2. ChatGPT 会话已经确定的架构输入

从会话《通信协议框架设计》中，可以直接继承以下设计原则：

- 协议独立于 CAN、CAN FD、RS485 等底层链路。
- 上层统一使用请求/响应、周期数据、事件通知和任务结果几种消息语义。
- 统一消息至少要有协议版本、服务/消息类型、源节点、目的节点、对象或参数标识、序号、标志位、
  payload 长度、payload 和完整性字段。
- 控制、参数、任务、诊断、升级必须拆成独立服务；参数读写或升级不能阻塞周期控制。
- 电机控制命令应通过统一控制状态机进入电机服务，不允许通信直接修改 FOC 全局变量。
- 辨识、标定和模态识别采用异步 Job 模型：`START`、`GET_STATUS`、`CANCEL`、`GET_RESULT`。
- 固件升级是独立服务：准备、传输、整体校验、激活、重启确认和失败回滚。
- 控制周期、状态周期、闭环位置、节点数量、原始数据规模和断连策略必须先冻结，再定最终带宽和帧布局。

这些是架构结论，不是公司已经批准的 type 编号、CAN ID 或 CRC 细节。

## 3. 飞书协议应如何映射到这个框架

飞书文档给出的统一外层是：

```text
统一应用帧 = 16B 帧头 + payload + 2B CRC16
```

其中帧头包含 magic、version、flags、src_id、dst_id、type、seq_id、len、reserved 和 CRC8。
CAN FD 的 64 字节数据区对应 `16B 头 + 46B payload + 2B CRC16`。因此 CAN FD 只是统一应用帧的
一种承载方式：

```text
MotorCommand
  → Service 编码为统一 payload
  → yg_protocol_frame_t 添加统一头和 CRC
  → CAN FD adapter 映射为 29 位 ID + FD data
  → 发送
```

反向接收过程为：

```text
CAN FD frame
  → 校验 ID / DLC / FD / BRS 元数据
  → yg_protocol_frame_t 解码和 CRC 校验
  → 按 src/dst/type/seq 分发
  → Service 校验业务条件
  → 生成 ServiceResult 或 StatusSnapshot
  → 重新编码为统一应用帧
```

对于 RS485 和以太网，不复制一套业务协议，只替换最后的链路适配层。RS485 需要增加字节流分帧、
主从轮询和响应超时；以太网需要明确 TCP/UDP 会话、报文边界和丢包策略，但业务 payload 保持一致。

## 4. 现在不能直接定死的事项

飞书文档和会话中有几处必须列为“协议决策”，不能由实现者自行猜测：

| 项目 | 当前信息 | 处理方式 |
| --- | --- | --- |
| flags 位 5/4 语义 | “需要 ACK”和“ACK 帧”描述存在重叠 | 定义位图和 ACK 示例后冻结 |
| CRC8 覆盖范围 | 写成帧头校验，但是否包含自身未完全明确 | 给出算法伪代码和向量 |
| CRC16 覆盖范围 | 文档写覆盖帧头+payload | 明确是否包含 magic、CRC8，不得靠实现猜 |
| `len` 语义 | 表中偏移和文字说明不一致 | 固定为 payload 长度还是整帧相关长度 |
| type=100～199 | 电机段已预留，但具体命令表为空 | 由公司登记后使用，不能直接套旧 CAN 参数 ID |
| 分片重组键 | 文档提到 `(src_id, type)` 和 seq 片序 | 明确同一来源同一 type 的并发会话规则 |
| CAN FD 位时序 | 文档给出仲裁 500 kbit/s、数据 2～5 Mbit/s | 以收发器、布线和板级测试结果为准 |
| RS485/以太网 | 主文档没有完整适配规范 | 先定义适配契约，再实现，不假设已存在 |
| 升级整体安全性 | 分片 CRC 不等于镜像真实性 | 增加整包 hash、签名、防回滚和双镜像策略 |

## 5. 推荐的开发顺序

不要从“先列所有电机命令”开始，而应按依赖关系建立框架：

### 第一步：冻结协议契约

输出统一帧头、flags、CRC、len、type 注册、Node ID、错误码、版本和分片状态机。只写文档、C 类型
定义和黄金向量，不接入电机控制。

### 第二步：实现纯协议核心

实现无 HAL 的 `yg_protocol_frame_codec`、CRC、CAN ID codec、分片/重组和 native 测试。此阶段验证的是
“字节是否正确”，不是“电机是否运动”。

### 第三步：实现 CAN FD 适配器

实现 `CommHwCanFrame` 能力、29 位扩展 ID、FD/BRS、DLC、RX/TX 有界队列和错误统计。此阶段只做
loopback、mock 或台架收发，不调用电机控制服务。

### 第四步：实现消息路由器和只读服务

先接入心跳、设备信息、协议版本、能力查询和状态读取。这样可以验证路由、权限、序号、ACK、错误码
和状态快照，而不会因为控制逻辑复杂导致协议基础无法定位问题。

### 第五步：接入最小控制命令

按 `STOP/DISABLE → ENABLE → SET_MODE → SET_TARGET → watchdog` 顺序接入。位置、速度、力矩目标
建议共用一个控制命令外壳，由 mode 决定有效字段，避免每个模式复制完整协议。

### 第六步：接入参数、任务、标定和诊断

参数使用 ID 和事务；标定/辨识使用 Job；大数据使用受限分片；快照反馈使用统一状态对象。

### 第七步：接入升级

复用统一帧和分片，不复用电机控制路径。升级必须有 loader 边界、镜像 hash/签名、断点、回滚和
“升级期间禁止运行电机”的状态约束。

### 第八步：做多轴和 1 kHz 容量验证

至少 5 轴、每轴 1 kHz 控制与反馈属于总线容量和调度问题。先测利用率、最坏排队延迟、抖动和同步
误差，再决定是否需要分组状态、时间戳、双总线或其他方案。

## 6. 最终应形成的五份正式产物

1. **协议主规范**：统一帧、字段、CRC、版本、节点、type 和分片规则。
2. **服务与消息目录**：控制、状态、参数、诊断、Job、升级的 payload 定义和状态机。
3. **链路适配规范**：CAN FD、RS485、以太网分别定义承载约束，不重新定义业务语义。
4. **黄金向量与主机工具**：每个帧都有可复现的 encode/decode、错误和边界样例。
5. **兼容与迁移计划**：旧 11 位 CAN 与新统一协议的并存、切换、回滚和退役条件。

当前最合理的下一步是先完成第 1 份和第 2 份的骨架，确认上述未决项，再写 Stage 1 的纯协议 codec。
在这些决策冻结之前，不应继续扩展电机命令数量，也不应把候选 type 当成公司正式编号。
