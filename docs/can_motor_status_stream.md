# CAN 电机状态周期反馈

新增 32 字节 CAN FD 状态帧。与现有参数协议共用 11 位标准 ID、FD+BRS，仲裁/数据速率保持现有配置（默认均 1 Mbps）。所有多字节字段为**大端**。实现不修改 PID、Flash、标定或电机模式。

## 一条命令控制启停与帧率

命令 ID：`(node_id << 8) | 0x64`；数据长度 4 字节，大端 float32，与现有参数命令格式一致。

| 命令数值 | 行为 |
| ---: | --- |
| 0 | 停止周期反馈，保留已配置帧率 |
| 1 | 以已配置帧率启动/恢复（初始为 20 Hz） |
| 10～200 的整数 | 配置为该 Hz，并启动周期反馈 |
| 其他值、非整数、NaN/Inf | 拒绝，原状态和帧率不变 |

上电**默认关闭**，预设帧率 20 Hz。命令只改 RAM；重启后重新发送启动命令。

每条命令通过 `(node_id<<8)|0x65` 返回 4 字节大端 float32：成功时为当前有效 Hz，关闭时为 0，非法命令返回 −1。也可发送同 ID 的 4 字节零数据查询当前有效 Hz。命令回复是普通优先级回复，不是下面的低优先级状态帧。

| 操作 | roll 命令 ID | pitch 命令 ID | 4 字节数据（十六进制） |
| --- | --- | --- | --- |
| 启动 20 Hz | 0x364 | 0x464 | `41 A0 00 00` |
| 启动 10 Hz | 0x364 | 0x464 | `41 20 00 00` |
| 启动 200 Hz | 0x364 | 0x464 | `43 48 00 00` |
| 按已配置帧率恢复 | 0x364 | 0x464 | `3F 80 00 00` |
| 停止 | 0x364 | 0x464 | `00 00 00 00` |

## 低优先级反馈帧

反馈 ID：`0x7F0 + node_id`，因此 **roll=0x7F3、pitch=0x7F4**。节点有效范围 0～7。此段 ID 专用于状态反馈，不按原“高 3 位节点＋参数字节”解释。

CAN FD 长度 **32 字节**，DLC 编码为 13。

| 字节偏移 | 字段 | 类型 | 每计数单位 / 含义 |
| ---: | --- | --- | --- |
| 0 | 电机故障状态 | uint16 | 原 ErrorNow 故障枚举，0=无故障 |
| 2 | 电机控制模式 | uint16 | 原 ModeNow 枚举，0=停机、2=速度、3=串级位置、18=阻抗位置 |
| 4 | 目标位置 | int32 | 0.001 rad；外部命令 posRef |
| 8 | 位置反馈 | int32 | 0.001 rad；编码器连续机械位置 |
| 12 | 目标速度 | int32 | 0.001 rad/s；外部命令 speedRef |
| 16 | 速度反馈 | int32 | 0.001 rad/s；位置模式取实际控制使用的滤波速度，其他模式取编码器速度 |
| 20 | 电流参考 | int16 | 0.001 A；Iq 指令 |
| 22 | 电流反馈 | int16 | 0.001 A；实测 Iq，不是母线电流或相电流 RMS |
| 24 | 规划后位置参考 | int32 | 0.001 rad |
| 28 | 规划后速度参考 | int32 | 0.001 rad/s |

位置模式下，“目标速度”仍是外部 speedRef 字段，通常为 0；不能拿它替代位置轨迹的速度。串级位置模式的规划速度取 `trajectory_speed_reference`，不取含位置误差纠偏量的 `speedShadow`。模式 18 的规划值取该控制器的轨迹；速度模式只提供规划速度，无规划位置。停机或尚无有效规划时，规划字段标记为无效。

换算为 SI 值后乘 1000，向零截断；编码过程饱和而不回绕。int32 最小值 `0x80000000` 和 int16 最小值 `0x8000` 专用于“无效/不可用”；非有限值也编码为此标记，上位机不得把它画成 0。其余编码范围分别为 ±2147483647、±32767。

## 时序与优先级

- 电机模块按需在快环结束处发布一次一致快照，最多按请求帧率采样；快环不打包、不调用 CAN、不等待。主循环完成定点转换与发送。
- 1 ms 时基加相位累加，支持 10～200 的所有整数 Hz，包括不能整除 1000 的帧率；处理时钟 uint32 回绕。启用/改帧率后从新周期开始，不立即补发历史帧。
- 0x7F0～0x7F7 的数值高于当前所有控制/查询帧，CAN 仲裁优先级较低。硬件发送模式改为按 ID 排序的 TX Queue；后到的普通回复可排在尚未发送的状态帧之前。
- 状态帧只在没有普通回复待处理且硬件 TX 队列全空时尝试入队；忙则丢弃本次状态，不重试、不累积待发状态。已在总线上发送的帧无法抢占；停止命令前已入硬件队列的一帧仍可能发出。
  STM32G4 的 TX Queue 模式用 `HAL_FDCAN_IsTxBufferMessagePending` 检查全部三个发送缓冲区。实测空队列 `TXFQS.TFFL=0`，不能用 FIFO 空闲数等于 3 作为发送条件，否则周期帧永远被跳过。
- 反馈不替代主机心跳。接收路径忽略其他轴状态帧，既不将其解析为控制命令，也不因此刷新控制通信超时。主机需要持续向每台电机发送正常控制命令，或在静止观察时发送正常查询以满足既有 CAN 超时。
- 这是低优先级、允许丢周期的遥测；200 Hz 是空闲时的计划频率，不承诺总线拥塞时仍能达到。接收端记录本机/分析仪时间戳；本帧没有同步触发、序号或板端采样时间戳。

## 主机使用与验证

`tools/can_motor_status.py` 提供离线命令生成和状态解码：

```powershell
python tools/can_motor_status.py command --node 4 --value 20
python tools/can_motor_status.py decode --id 0x7F4 --data "00070003 fffffb1e 000005dc 000009c4 fffff830 04e2fa24 000002ee fffffe0c"
```

SDK 必须接收 32 字节 CAN FD 帧。旧上位机若只保留 `length==4` 的帧，会直接丢掉本反馈，需要据 ID/长度分流；原参数回复仍为 4 字节。

主机 C 检查：实际编码器金向量、全部 191 个整数帧率、启停与非法命令、回绕、快照握手、过期数据、不补发积压、实际电机字段来源、实际 RX 对 0～64 字节/远程/扩展帧的拒绝、HAL TX 优先级/满队列/失败不重试。另保留 Python 编解码和既有位置控制/RTT 回归。实机接收频率、总线负载和新增快环耗时需要下载后测量，构建与主机测试不能替代这些实测。

## 通信故障处理补充

2026-09-10 后续实机保持测试出现适配器 `CAN_ERR_FLAG` 接收记录，分别涉及 roll 和 pitch。板端记录过 Stuff Error、错误警告及错误被动状态；物理链路根因仍未确认。这些实测不能作为无故障长时间运行验收。

本次软件修正：心跳使能按当前闭环模式重新计算，停机或关闭心跳后解除计时并归零；闭环超时计数饱和，且仅在无其他故障时上报断连。解除计时不主动清除既有故障，正常接收恢复时仍沿用原断连清除流程。保护范围仍为电流、速度、串级位置及阻抗位置模式，不改变超时配置或增加自动重新使能。

主机遇到 SDK 错误标志立即中止测试。先发送两轴 STOP，再在原适配器会话关闭前读取 SDK 错误/状态信息，并记录完整 ID、FD flags、ESI、数据及时间戳。ERR 与 ESI 分别保留；API 不可用或读取失败不记成零错误。原始错误记录最多保存前 32 条，另记总数量，防止持续故障使内存无界增长。诊断接口可能具有读清语义，应结合首次快照、返回码和原始记录分析。
