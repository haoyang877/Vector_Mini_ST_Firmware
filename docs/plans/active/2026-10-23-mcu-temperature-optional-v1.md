# 新板MCU温度可选策略 v1

## 用户目标与当前阻点

用户要求暂时忽略MCU温度并继续新板适配。既有要求冻结中间层和BSP接口。
现有硬件端口没有经过逐板标定的有效MCU温度；采样诊断与保护资格分开，共享软件仍将温度
列为必需项：100ms缺样本产生故障17，状态输入、自检及故障恢复也依赖有效温度。
只改驱动无法满足目标；不能提供虚构温度或把NTC冒充MCU温度。

用户已明确允许温度策略相关的最小中间层修改例外。
初始代码交付只进行离线验证；后续用户另外授权了关相烧录与复位验收，
最终实机结果见文末。整个过程没有驱动电机。

## 最小例外的实现

1. 板级只读配置区增加“是否要求MCU温度”的编译期策略。
   旧板默认必需；新板关相调试目标显式选择临时可选，恢复测温时切回必需。
2. `foc_sensing.c`根据策略决定是否报告MCU缺样本/过温故障，
   温度样本资格仍按真实采样产生，无数据仍为NAN和无效。
3. `motor_state_machine.c`按策略计算运行准入与必需自检项。
   温度自检位没有测量时保持未通过，不能伪造成功；只从本目标必需项中排除。
4. `motor_fault.c`同步温度来源故障的显式CLEAR资格；
   不自动清除已锁存故障，不影响其他故障来源。

不修改BSP函数、类型、单位、时序契约，不修改控制算法、参数/协议ABI、
相电流/电压保护、绕组热模型或功率输出锁。原有CAN温度无效哨兵继续有效。

## 验证与回退

- 旧板温度正常、超温、100ms超时、故障恢复的原有测试必须保持。
- 新策略缺样本持续超过超时不产生故障17，但遥测仍无效。
- 自检不能把缺失温度报告为有效，也不能跳过电压、电流、编码器及配置条件。
- 其他故障仍能置位并关相；临时策略不解除App_Off的编译期功率锁。
- 双板编译、相关原生测试与仓库PR检查分别记录结果。
- 回退配置即可恢复温度必需；未获进一步授权不变更当前板上固件。

## 配置与可观察行为

`BOARD_REQUIRE_MCU_TEMPERATURE`是板级只读策略：旧板固定为1；
新板默认也为1。只有完整App_Off工程显式设置
`R40_APP_MCU_TEMPERATURE_OPTIONAL=1`时才为0。
该临时开关仅允许与`R40_APP_PHASE_LOCK=1`组合，否则编译拒绝；非法开关值也编译拒绝。
其他新板工程不继承这次放宽。既有内部温度ADC诊断开关不变。

可选策略不改`MotorTemperature_IsFresh`语义，不修改NaN、有效位、超时计数或滤波。
自检状态仍保留温度事实位，未测到时是0；只在完成判定中排除此项，
其余七项以及未知位的拒绝条件保持。
已锁存的温度故障只允许由原显式CLEAR流程处理，不在后台静默清除。

## 后续授权的实机验证与默认值修正

用户随后明确授权烧录、复位并验证完整APP，始终关相。
首个温度可选镜像读回校验通过，参数区未变；故障17消失，
但自检出现故障18。只读CAN返回自检位0xCF，缺少温度位和配置有效位。
PA4偏置完成128点校准且采样有效，温度无效哨兵正常。

读取真实活动配置确认：默认应用电流上限仍为6A，而新板允许上限为3A，
电机R/L、磁链和1.6A校准电流均正常。这是默认配置不合法，不应绕过配置自检。
因此仅修正`application_profile_defaults.h`中的默认值选择：
`min(6A, 板级允许上限)`。旧板6A保持，新板首次默认值为3A；
参数结构、已保存值的校验/装载和保护规则不变。

新增回归直接调用生产`Param_Return_Default`和`ParameterValue_ConfigurationValid`，
验证新旧板真实默认值均合法、未自动确认配置/编码器，以及超限仍被拒绝。
可选温度状态机夹具也改为采用真实默认值，避免手填3A掩盖这一问题。
首轮实机记录保留在`outputs/at32f456-port-v1/mcu-temperature-optional/hil-20261023/`，
修正候选须独立归档并重新验证，不覆盖首次故障证据。
