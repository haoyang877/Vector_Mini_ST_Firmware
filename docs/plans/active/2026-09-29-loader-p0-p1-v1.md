# Loader P0/P1 实施计划 v1

基线：`83f5aae0`，独立分支 `codex/loader-p0-p1`；交付后合入 `codex/system-refactor`。

## 目标与顺序

1. P0：冻结 Loader、配套 APP、schema12 与升级包；发布版本来自统一构建输入。
2. P0：最小 CAN FD 客户端完成身份检查、进入 Loader、下载、重试、激活及新 APP 确认。
3. P0：正常升级、断电、故障 APP 救援、丢帧/错误绑定及参数保护验证。
4. P1：真实身份/版本查询，持久 SN 与电机类型，明确生产与普通用户权限。
5. P1：持久激活门槛及一次试运行确认；单槽失败留 Loader，全擦重传，没有旧 APP 回滚。

## 设计决策

- 升级容器 v3、描述符 v3、布局5，参数 ABI 仍为 schema12/4304B。拒绝 v1/v2，不能混用
  旧 Loader；先通过 SWD 安装配套 Loader，再升级 APP。Flash 分区不移动。
- 描述符扩至96B，包含三个独立8B提交单元：激活、试运行已开始、APP已确认。
  下载包中的三个单元均为 FF；Loader跳过这些单元，CRC计算也按FF归一化。
  每个单元只写一次并读回，禁止对半写或 ECC 损坏单元补写。
- 对应 ACTIVATE 回复物理发送完成后才写激活标记；完整但未激活镜像永不冷启动。
  Loader在首次跳转前写尝试标记；掉电或复位后未确认则驻留 Loader。
- APP基础健康连续保持至少1s后，接受主机对版本和CRC的显式确认；仅数字关相和保存空闲
  时写确认单元。客户端必须重新查询确认状态才能报告成功。
- 参数最后一个2KiB页单独保存生产身份，不更改校准记录，APP参数保存不得擦到该页。
  SN/电机类型通过显式SWD生产流程配置；CAN只读，普通参数写不开放这两个字段。
  CAN ID仍由现有schema12参数所有者管理，身份记录不重复存储CAN ID。
- MCU细节只在platform/ports；通用镜像内核只接收Flash能力与安全端口。
- 不增加UART、第二款MCU、断点续传、A/B回滚、签名或GUI。

## 验收与证据

原有单槽、输出关闭、会话绑定、物理TX票据、CRC32、schema12语义保留。
新增纯内存断电切点测试、黄金向量、真实CLI离线模拟、错误目标/版本/CRC测试。
运行format、lint、PR与release验证；独立构建普通APP、配套APP和Loader，记录ROM/RAM与哈希。
用户明确本轮只做代码和离线验证，正在自行验证APP；本任务不打开J-Link/USBCAN。
后续硬件测试须另行授权独占台架，先STOP/关相和备份全部Flash/参数，结束恢复测试前内容。
未完成实机项目明确标为待验，不使用历史日志替代。

## 回退

源码回退本分支提交；部署通过备份恢复整片原有固件与参数。Flash几何未移动，但v3部署
前必须保留旧Loader与APP配套备份，不能只替换任意一端。升级失败不自动恢复电机运行。

## 实施状态

开发中。当前实机由“T-固件实机测试”占用；本任务先执行离线开发与构建。
